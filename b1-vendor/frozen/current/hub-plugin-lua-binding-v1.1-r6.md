## A. Binding rules (the Lua host's language mapping; normative for host 1)

- **LB-1 Names.** Call `area.name` (CA-1) is `botster.area.name`. No `capabilities.` prefix (grants stay enforced by the Hub).
- **LB-2 Arguments.** One table. Unknown keys are `invalid_request`. *Test: `conf::lb_2_unknown_argument_key_is_invalid_request`.*
- **LB-3 Results.** Every call returns `{ ok = true, value = <v> }` or `{ ok = false, error = { kind, message, retryable, effect, detail? } }` (section 14). `kind` is one of the eleven closed kinds; a plugin branches on `kind` and `detail.code`, never on `message` (ER-3). `effect` (`none|committed|unknown`) is on every failure (ER-5). LN-1 lists `kind`, `detail` and `effect` but omits `message` and `retryable`; section 14 is authoritative (finding F-8). Only a programming error raises (LM-4). The plugins' `pcall(fn, args)` wrappers go away.
- **LB-4 Handlers.** `call = function(payload, request)`. `request` is read-only and Hub-owned: `caller`, `origin`, `id`, `deadline_ms`. For a tool `payload` is the validated arguments. For an event `payload` is the EV-15 record `{ owner, name, subject?, priority, source, payload, at }` (`at` Hub-stamped), so the plugin's own data is `payload.payload` (today workspaces' `session_family` handler receives the frame directly as its argument).
- **LB-5 Identity and references (WF-6).** `request.caller` is one of `{ kind = "operator", credential_id?, hub_id? }` (`credential_id` is present for a WebRTC credential and **absent for a Unix-socket operator** identified by peer uid, HP section 7, VC-1), `{ kind = "session", session = { hub_id, session_id } }`, `{ kind = "plugin", plugin_key, instance }` (the callee of `plugins.call`: the **authenticated identity of the calling plugin instance**, taken by the Hub, never from `args`; the caller's own caller is not forwarded, PC-2) or `{ kind = "system" }`. The Appendix B shape is `{ kind, credential_id?, hub_id?, session?, plugin_key?, instance? }`. A callee applies its own policy over `request.caller` and never over a field in `payload`. One spelling: **a row's own identifier is `id`; a reference to another resource names its kind** (`session_id`, `target_id`, `operation_id`). So a session row has `id` and a session reference is `{ hub_id, session_id }`; to reference a row a plugin writes `{ hub_id = row.hub_id, session_id = row.id }`. A plugin reads identity from `request.caller` only (VC-6). *Tests: `conf::lb_5_caller_and_reference_spelling`, `conf::lb_5_plugin_caller_variant_is_preserved`, `conf::lb_5_operator_credential_id_is_optional`.*
- **LB-6 Events (EV-2, EV-15, A4r7).** `botster.events.on(pattern, opts?, fn)` is valid only while the entrypoint runs (before `register` returns; later it returns `{ ok = false, error.kind = "invalid_request", detail.code = "registration_after_ready" }`). `pattern = { owner, name }` (`*` and a `.*` suffix allowed); `opts = { subjects = "own"|"any", min_priority = "low"|"normal"|"high", handler_id? }` (`min_priority` defaults to `low`). Each call registers one `event` handler (a stable host-made `handler_id`, or `opts.handler_id` when the plugin names it) and adds `{ handler_id, pattern, subjects?, min_priority? }` to `Ready.events.subscribed`; an unknown `handler_id` fails the load. `botster.events.on_gap(fn)` registers the one `event_gap` handler (`Ready.events.gap_handler`): `fn(gap, request)` with `gap = { gap_id, owner, name, subject?, count, lost_bytes?, recovery = "state"|"unavailable"|"partial", state_read?, aggregated? }` (A4r8: `resync` is gone; A4r9: `gap_id`, `count` is the number of lost events and `lost_bytes` is present for the output tap; J4b dropped `lost_events`). After a handler failure the Hub retries with the SAME `gap_id` and summary, so a plugin makes its resync idempotent on `gap_id`; it receives every gap regardless of `min_priority`, and a gap obligation stays until it returns success. `recovery = "state"` means a readable authoritative state exists (the session family baseline, `sessions.list`, the plugin's own store or `operations.get`, or the producer's declared `state_source`): the plugin resyncs from it. `"unavailable"` (a foreign event with no `state_source`) and `"partial"` (an aggregated gap) mean the plugin cannot rebuild; it must treat the loss as permanent and may surface it. The manifest event declaration has an optional `state_source = { read, grant }` (MN-3, EV-12) and optional `keyed` and `priority`. `events.subscribed[]` in the manifest and in `Ready` has the same fields as `opts` (MN-3). Handler-table form: `handlers = {{ kind = "event", id, pattern, call }}`, same thing.
- **LB-7 Operations (CA-16).** `botster.operations.on(fn)` (load-time) sets `Ready.operations.subscribed`; `fn(record, request)` receives the LB-13 record, with `request.origin = "operation"`. A plugin that does not register it gets no notifications and uses `operations.get` only for reconciliation.
- **LB-8 Bytes and ids (section 17, LN-1).** Appendix A takes **`bytes_b64`**: `sessions.write{ session, bytes_b64 }`; `http.request` takes `body_b64` and returns `body_b64`; `ws.send` takes `data_b64`. The plugin encodes and decodes with the host-local `botster.base64.encode{ bytes }` and `botster.base64.decode{ text }`. (A4 said the host converts a Lua byte string; A4r29 does not: the argument names are exactly those of Appendix A.) `botster.ids.new{}` returns a fresh 128-bit id (26 lowercase base32) from the OS CSPRNG. **Crypto (language-local, LN-1):** `botster.crypto.sha256{ bytes_b64 }` returns `{ digest_b64 }`, `botster.crypto.hmac_sha256{ key_b64, bytes_b64 }` returns `{ mac_b64 }`, `botster.crypto.random_bytes{ n }` returns `{ bytes_b64 }` (section 17). A plugin encodes a Lua string with `botster.base64.encode` first. Errors: `invalid_request` for bad base64, or an `n` or size whose base64 does not fit `max_result_bytes`; `unavailable` if the host has no CSPRNG. All return the LB-3 envelope. All host-local helpers return the LB-3 envelope and never send a frame (LH-1).
- **LB-9 JSON.** Host-local: `json.encode{ value }`, `json.decode{ text }`, both returning the envelope; `json.array{ ... }` (or `json.empty_array`) constructs an array (today two plugins decode `"[]"` to get one). **The empty-table-as-array rule lives here and nowhere in the contract (EN-7 was removed in A4r29):** an empty Lua table encodes as a JSON object `{}` unless it came from `json.array` or `json.empty_array`; a plugin that needs `[]` uses one of those.
- **LB-10 Registration.** `botster.register{ tools, prompts?, resources?, handlers }` builds `Ready`; `call` functions stay in the host's table by handler id (IV-8). Handler kinds (section 24 origins): `tool`, `prompt`, `event`, `event_gap`, `entity_provider`, `ui_action`, `timer`, `store_watch`, `operation`, `webhook`, `relay`, `fs_watch`, `command`, `hook`. `webhook` needs the `net` grant with scope `net_inbound` (CP-2). **Load-time helpers** (LN-1): `botster.register`, `botster.events.on`, `botster.events.on_gap`, `botster.operations.on`, `botster.webhooks.on(path, fn)`, `botster.relay.on(fn)` (WP-2) and `botster.fs.on_watch(handler_id, fn)` (FS-3). A call after `Ready` returns `invalid_request{detail.code: registration_after_ready}` (A4 used `failed` and `wrong_context`). `botster.webhooks.on(path, fn)` registers `handlers[{id, kind = "webhook", descriptor = {path}}]`; `fn(payload = {path, headers, body_b64}, request)` returns `{status = 100..599, ...}` as the HTTP answer (NT-7). *Test: `conf::lb_10_register_builds_ready_and_refuses_after_ready`.*
- **LB-11 Network and secrets (new, NT-1 to NT-9, Appendix C).** `botster.http.request{ method, url, headers?, body_b64?, timeout_ms, max_response_bytes? }` and `botster.ws.open{ url, headers?, subprotocols? }` are asynchronous: each returns `{ operation_id, kind, state = "queued", terminal = false }` at once. The completion arrives on `operations.on` (LB-7) and through `operations.get` as `{ kind = "http", state = "done", terminal = true, status, headers, body_b64 }` or `{ kind = "ws", state = "open", ws_id }`. `ws.send{ ws_id, text? | data_b64? }` returns `{ accepted }` or `backpressured`; `ws.close{ ws_id, code?, reason? }`. Received frames and the close arrive as **events** owned by `net` (`net/ws.message` and `net/ws.close`), so a plugin subscribes with `events.on({ owner = "net", name = "ws.*" }, fn)`. `botster.secrets.get{ name }` returns `{ value }` for a declared secret (grant surface `secrets`). Manifest: `capabilities` entry `{ surface = "net", scope = "net", allow = {...} }`; scopes `net_private` and `net_inbound` are separate grants; `secrets = {{ name, required? }}`. *Test: `conf::lb_11_http_and_ws_are_async_operations`.*
- **LB-12 Sessions beyond spawn.** `botster.sessions.create_command{ argv, cwd?, env?, size?, interaction? }` (scope `session_create_command`, bare only) returns `{ operation_id, session, state, terminal = false }`. `sessions.terminal_state` and `read_cursor` (scope `session_observe[:any]`) and `read_screen` (scope `session_screen[:any]`) read; `sessions.stop`, `delete`, `update`, `restart` need their own scope. **A restart that cannot run fails `failed{detail.code: wrong_state}` with a reason of `not_ended`, `not_restartable`, `record_unavailable`, `environment_not_retained` or `not_ready`** (there is no `wrong_state` kind; `wrong_state` is a `detail.code` under kind `failed`). Observation events (SO-3, EV-14): `hub/session.activity`, `hub/session.modes`, `hub/session.size`, `hub/session.silent` and `terminal/title|cwd|bell|notification|prompt_mark|modes|exit` (`terminal/exit` is high; `terminal/modes` is normal and keyed by session); they need `session_observe[:own|:any]` or `events_terminal`. *Test: `conf::lb_12_session_calls_and_scopes`.*
- **LB-13 Operation records (CA-16, Appendix C).** `operations.get` and `operations.on` deliver one record: `{ operation_id, kind = "spawn"|"safe_write"|"http"|"ws"|"process"|"plugin_call", state, terminal, session?, worktree?, reason?, probe_written?, residue? = "none"|"possible", text_written_bytes?, status?, headers?, body_b64?, ws_id?, exit_code?, signal?, stdout_tail_b64?, stderr_tail_b64?, truncated?, duration_ms?, result?, error?, effect? }`. A plugin decides finality only from `terminal`, never from a state name. *Test: `conf::lb_13_operation_record_shape`.*

- **LB-14 Commands and other plugins (PX-1, PC-1; new since A4r29).** `botster.process.run{ argv, cwd?, env?, timeout_ms, stdout_tail_bytes?, stderr_tail_bytes? }` (scope `process_run`) runs one command without a shell and is **asynchronous**: it returns `{ operation_id, kind = "process", state = "queued", terminal = false }`. `cwd` is `{ target_id | worktree_id, relative? }`, never an absolute path. The terminal record (LB-13) carries `exit_code?`, `signal?`, `stdout_tail_b64`, `stderr_tail_b64`, `truncated`, `duration_ms`. A plugin that used `os.execute`, `io.popen` or a blocking gate runner changes to this call and an `operations.on` handler (project-pipelines gate runner, workspaces shell steps). `botster.plugins.call{ interface, tool, args, idempotency_key?, timeout_ms? }` (A4r72 PD-5: **an interface, not a plugin**; scope `plugin_call:<owner>` derived from the resolved provider) is asynchronous too (`kind = "plugin_call"`); the terminal record has the callee's `result` or a typed `error`. `tool` must be a call of the resolved interface, else `capability_denied{detail.code: undeclared_dependency}`; the provider is the one approved at install (`Hello.bindings`). The callee must declare `callable_by = {"plugins"}` on the tool, else the call is `not_found`. While the provider is unloaded the call is `unavailable{provider_unloaded}`; after an accepted breaking update it is `unavailable{requirement_unmet}`. Use an `idempotency_key` for a durable post (for example into the messaging plugin). *Test: `conf::lb_14_process_and_plugin_call_async_and_typed`.*
- **LB-15 Files, assets and web pages (FS-1 to FS-3, AS-1 to AS-4, WP-1 to WP-5).** `botster.fs.list/stat/read` (scope `fs:<root id>`; the manifest declares `fs_roots = {{ id, read = true }}`) are synchronous reads; `fs.read` returns `{ bytes_b64, eof }`. `botster.fs.watch{ root, path, handler_id }` needs a handler registered with the load-time helper `botster.fs.on_watch(handler_id, fn)`; `fn({ watch_id, root }, request)` is level-triggered (re-read what you need); re-arm after a reload comes from `Ready.fs_watches`. `botster.assets.publish{ name, content_type, bytes_b64 }` returns `{ asset_id }` and `botster.assets.lookup{ name }` returns `{ asset_id, content_type }` (scope `assets`, named "publish web pages"; the manifest may also list `assets = {{ name, path, content_type }}`); a page is one self-contained asset. The ui-contract `embed` part names the asset. `botster.web.set_origin{ origin }` (scope `web_origin`) sets the origin that pairing URLs use: an `https` origin, a loopback `http` origin, or `{ served = true }` (the plugin's own served origin, WP-5). **`origin = nil` CLEARS the origin: the Hub has no default origin, and with none set it refuses `issue_pairing` with `wrong_state{no_web_origin}` (client PR-0)** (J4 WP-1; it was "restores the default" in A4r77). `botster.web.set_ice_servers{ servers }` (same scope) and `botster.relay.open{}` / `botster.relay.deliver{ relay_id, envelope_b64 }` with the load-time `botster.relay.on(fn)` (scope `relay_signaling`) serve the signalling relay. `fn({ relay_id, envelope_b64 }, request)` forwards an opaque envelope. The two Hub-owned exceptions on a served origin (WP-5) are `POST /hubs/<hub_id>/signal` and `GET /hubs/<hub_id>/ice`; everything else on it is the plugin's. Static routes: manifest `static_routes = {{ route, root, index? }}` (scope `net_serve`). *Test: `conf::lb_15_files_assets_web_relay_shapes`.*
- **LB-16 Other calls (Appendix C).** `botster.secrets.put{ name, value | nil }` needs the secret declared `plugin_writable`; `botster.worktrees.delete{ worktree_id, delete_branch? }` (scope `worktree_delete[:any]`); `botster.sessions.write` returns `{ state = "written"|"partial"|"cancelled"|"failed"|"unknown", accepted_bytes, written_bytes?, max_written_bytes?, reason? }`; plugin-visible session rows carry `owner`. MCP proxy: the manifest `mcp_servers` (MP-1; scopes `mcp_proxy`, `mcp_proxy_stdio`) makes the Hub list the server's tools under namespaced names; a plugin needs no Lua for it. *Test: `conf::lb_16_other_call_shapes`.*
- **LB-18 Plugin definition (PD-1 to PD-8, new since A4r70).** The manifest now reads as a contract. `version` is semver (`manifest_bad_version` otherwise); optional `description`, `license`, `source`. `requirements = { botster_plugin_api, features = { required, optional }, ui_contract? }` is checked before any code runs (`api_unsupported`, `feature_missing`, `ui_contract_unsupported`); an absent optional feature is reported in `Hello.features`. `provides = {{ interface = "name@M.m.p", exports = {{ tool, args_schema, result_schema, effect }} }}` declares the tools that implement an interface; compatibility with the interface is exact and deterministic and **recursive** (PD-3b: equal `effect`; the same rules for nested `properties` and `items`; provider `required` a subset for args and a superset for results; **only `type`, `properties`, `required`, `items`, `enum`**, for the interface and for the provider's declared exports alike; any other keyword in an interface schema refuses the interface). **v1 interfaces are calls only** (events and kinds are refused). An interface document ships with the provider at `interfaces/<name>@<version>.json`; there is no catalog kind `interface`. **Three validation stages (PD-9):** (A) static admission at install or update, **no plugin code runs**: manifest schema, identity, API/features/ui_contract, exports against interface documents, resolution of `requires`, derived grants, approval; (B) enable bootstrap, the first time code runs: what the plugin registers in `Ready` (tools, handlers, events) **must match its declared exports**, else the registration is rejected before `Activated` and the package is `errored`; (C) runtime. A plugin author therefore keeps `provides.exports` and the `botster.register` tools identical (workspaces, project-pipelines and messaging test this in the kit with `botster.plugins.bindings`). `requires = {{ interface, range, optional? }}` with a semver range. **Bindings.** `botster.plugins.bindings{}` (new in A4r77; no grant, own bindings only, **allowed during bootstrap**) returns `{ bindings = {{ interface, interface_version, provider, provider_version, interface_hash, state = "available"|"unavailable"|"unmet" }} }`. `Hello.bindings` and the lock carry `interface_version` **separately from `provider_version`**, and a `requires` range applies to the **`interface_version`**. An unmet optional binding has `provider = nil`. A consumer addresses the approved provider only through `plugins.call{ interface, tool, ... }`. **`plugins.call` dedupe** key is `(caller, interface, tool, idempotency key)`; a retry joins the first receipt (PC-4), so a plugin reuses one key per logical post. The Hub event `hub/plugin.dependency { interface, provider, state = "available"|"unavailable"|"replaced" }` (priority high, subject the consumer, scope `events_hub`) tells a consumer when a required provider changes; subscribe with `events.on({ owner = "hub", name = "plugin.dependency" }, fn)`. Errors a plugin handles: `undeclared_dependency`, `provider_unloaded`, `requirement_unmet`, and, at install, `requirement_conflict`, `ambiguous_provider` and `dependency_cycle`, which are `conflict{detail.code: ...}`, `interface_unknown_required` (a consumer fails closed on an unknown required field of an answer). **Handover and recovery (PD-8):** at a provider handover the Hub revalidates; recovery happens only with the **same bound provider** (no silent provider switch or new authority). The gap recovery of `hub/plugin.dependency` reads `botster.plugins.bindings{}` (state `available|unavailable|unmet`). Load order is dependency order (PD-7); a required cycle is refused before any code runs. *Test: `conf::lb_18_definition_and_bindings`.*
- **LB-16b Session update and spawn arguments (J4b, Appendix A).** `botster.sessions.update{ session, label?, task?, metadata? }` (scope `session_update[:any]`); a plugin writes `metadata` only in its own namespace (`metadata[<plugin key>]`, else `capability_denied`), and never the terminal title. `botster.session_types.spawn{ session_type_id, target_id?, worktree_id?, cwd?, environment?, prompt?, context? }` (Appendix A, CA-14): `environment` is `{ [name] = string }` with only names in the session type's `allowed_environment_overrides`, bounded by `max_env_bytes` (else `invalid_request`); `context` is `{ [key] = string }`. `ensure_worktree_and_spawn` is the same plus `worktree = { branch, base_ref?, reuse_worktree_id? }`. *Test: `conf::lb_16b_update_and_spawn_arguments_match_the_hp_rows`.*
- **LB-17 Manifest keys (MN-1).** A plugin writes one JSON object with only these keys: `botster_plugin_api`, `name`, `version`, `entrypoints`, `capabilities`, `session_types`, `config`, `secrets`, `fs_roots`, `static_routes`, `assets`, `mcp_servers`, `storage`, `events`, `entity_families`, `views`, `notice_reactions`, `scope` (`"device"` default or `"target"`), `session_actions_ui`, `limits`, and (section 25.3, PD-1 to PD-5) `description`, `license`, `source`, `requirements`, `provides`, `requires`. An unknown key fails the load `manifest_unknown_key`. `session_actions_ui` entries may carry `warning`, `effect` (`read|immediate|committed|accepted`), `durable_operation`, `applies_to`, `label_pointer`, `status_pointer`, `url_pointer`. `views` hold ui-contract documents (v1.0, v1.1 and v1.2 frozen). *Test: `conf::lb_17_manifest_keys_closed`.*

## C. What each plugin must change (mechanical unless stated)

- **Every plugin: manifest.** MN-1 allows only the listed top-level keys (`botster_plugin_api`, `name`, `version`, `entrypoints`, `capabilities`, `session_types`, `config`, `secrets`, `storage`, `events`, `entity_families`, `views`, `session_actions_ui`, `limits`; the complete list is LB-17, which adds `fs_roots`, `static_routes`, `assets`, `mcp_servers`, `notice_reactions`, `scope`, `description`, `license`, `source`, `requirements`, `provides`, `requires`); `storage.collections` (with `schema_version`, `accepts`, `indexes`) implies the own-storage grant, which is never written in `capabilities`. Capabilities are `{surface, scope?}` (MN-2); a bare session scope means `:own`.
- **workspaces.** Rename store calls (rows 5-8) and declare collections (`workspaces`, `membership` keyed `<hub_id>/<session_id>`, with an index on `workspace_id`); drop `entity_publish` sequence use (entity families become store projections, ST-7); subscribe with `events_hub` and `events_plugin:botster-orchestrator` through LB-6, reading `event.payload`; spawn returns accepted identity and records the ref (row 13). Pruning policy stays the plugin's (it prunes on explicit ended evidence; a failed accepted start stays as an ended/lost row until `sessions.delete`, CA-15).
- **orchestrator.** `ensure_worktree_and_spawn`/`spawn` results change (row 13); the tool returns `{ accepted, session, worktree?, operation_id }`; `session_spawned` emit keeps its declaration and adds `public = true`; `pcall` wrappers removed.
- **project-pipelines.** Store rows 5-8 with collections per family and indexes for the hot reads (by `ticket_id`, `run_id`, `status`); drop `meta/entity_seq/*` and the v3 migration; `ensure_worktree_and_spawn` accepted shape; `config.get` plain values; `load_state()` (60 call sites) must become indexed queries; `search_tickets` stays plugin code over bounded pages (ST-10).
- **messaging (rewrite, not rename).** The Hub has no inbox. It must own: an `envelopes` collection (document per envelope with `to_session`, `state`, `seq`, `lease_until`, `body`, `content_type`), indexes on `(to_session, state, seq)`, post = `store.put` (idempotent on an envelope id the plugin mints: see F-2), receive = query + lease via `store.batch` with revisions, ack = batch delete, access policy over `request.caller` (a session reads only its own inbox; `operator` has none), retention per SS-5 (keep across a restart of the same session id, refuse posts to an ended session, delete on deletion, reconcile against `sessions.list` after a crash, only from a ready baseline), and the doorbell through `sessions.safe_write`. The store write and the doorbell are no longer one atomic step (they were one Hub step with `messages.post`): persist the envelope, then `safe_write`; on load re-issue the doorbell for envelopes whose ring was never confirmed. Manifest: `{surface = "session_actions", scope = "session_safe_write:any"}`, `session_read:any`, `{surface = "events", scope = "events_hub"}`; drop `session_notify:any` (no caller) and `session_message`.
