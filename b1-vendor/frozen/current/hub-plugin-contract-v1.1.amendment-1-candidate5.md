# Hub→plugin contract v1.1: Amendment 1 (the package root and the manifest file), candidate 5

Author: plugin-platform writer (Claude, 00a2), 2026-09-30. Reviewer: Sol Hub B. Requested by the orchestrator after a user finding.
**Base:** the frozen Hub→plugin contract joint package J4e (`hub-plugin-contract-v1.1.joint-J4e.md`, sha256 `e16f3f6b60963fae0cf971e6f7e610a9b91be7ecf28c95f02e8530d2bde27f19`), which stays immutable. **This file is the amendment, in the post-freeze amendment path**: it adds clauses PK-1 to PK-9 and lists the exact edits to existing J4e clauses. Until it is accepted, J4e stands alone.

**The gap.** MN-1 fixes the **content** of a manifest (one JSON object with exact keys). No clause names the **file**, where it lives in a package, or how a source points at one plugin inside a repository that holds several. Plugin authors, catalogs and the package manager all depend on it, so it is contract.

## 1. New clauses (section 25.4: The package root and the manifest file)

| # | Clause | Test |
|---|---|---|
| PK-1 | **The manifest file.** The manifest of a plugin is the file **`botster-plugin.json`** at the **package root**: the exact name, case-sensitive, UTF-8 JSON, one JSON object (MN-1), at most **`package_bytes_max`** (the existing package bound of PM-4; the amendment adds **no new cap**). A manifest under any other name, or not at the package root, is not a manifest. | `conf::pk_1_manifest_is_botster_plugin_json_at_the_package_root`, `conf::pk_1_other_name_or_location_is_not_a_manifest`, `conf::pk_1_manifest_bounded_by_the_existing_package_bound` |
| PK-2 | **The package root, and the checks on `path` in two stages.** The package root is: for a **`local`** source, the directory that the source names; for a **`git`** source, the **repository root**, or **`path`** inside it when the source carries one. **`path`** is an optional relative path in a source and in a catalog entry. **Stage 1, before any fetch (syntax only):** it uses `/` separators, is not absolute, has no `.` or `..` segment and no empty segment, and is **within the existing request bound (`max_frame_bytes`; the amendment adds no cap)**; a violation is refused **`invalid_request{detail.code: path_invalid}` before anything is fetched**. **Stage 2, after the fetch (the tree):** `path` **names a directory inside the fetched tree**, and **a symlink that leaves the tree is refused** (PM-4); a `path` that names no directory is `failed{detail.code: path_not_found}` and one that resolves outside the tree is `failed{detail.code: path_not_contained}` (the client names both as `failed{reason: path_not_found}` and `failed{reason: path_not_contained}`; the reason is the `detail.code`), and **nothing is staged** in either case. **No stage promises that every bad path fails before the fetch**: only the syntax of stage 1 does. The package is **the files under its root only**: the rest of the repository is not part of the package, is not hashed (PM-3) and is not installed. | `conf::pk_2_package_root_is_dir_or_repo_root_or_path`, `conf::pk_2_stage1_path_syntax_refused_before_any_fetch`, `conf::pk_2_stage1_does_not_promise_that_every_bad_path_fails_before_the_fetch`, `conf::pk_2_stage2_path_not_a_directory_is_path_not_found`, `conf::pk_2_stage2_path_outside_the_tree_is_path_not_contained`, `conf::pk_2_only_files_under_the_root_are_package_files` |
| PK-3 | **Exactly one manifest per package root.** A package root holds **exactly one** package manifest file (PK-1, PK-6). A **missing** manifest fails validation `invalid_request{detail.code: manifest_missing}` and a **malformed** one (not UTF-8, not valid JSON, not one JSON object, or over `package_bytes_max`) fails `invalid_request{detail.code: manifest_malformed}`; **a manifest that is one JSON object but fails the schema keeps its specific code**: an unknown top-level key is `manifest_unknown_key` (MN-1), a bad version `manifest_bad_version` (PD-1), a bad scope `manifest_bad_scope`, a bad allowlist `manifest_bad_allow` and so on, and **only a schema failure with no defined code is `manifest_malformed{path}`** (`path` is the JSON pointer of the failure); **both before any code runs** (static admission, PD-9 (A)). **A manifest in a subdirectory is never read unless a `path` names that directory**: a repository whose root has no manifest and whose source has no `path` is `manifest_missing`, and the error says that `path` exists. | `conf::pk_3_exactly_one_manifest_per_root`, `conf::pk_3_missing_manifest_fails_before_any_code`, `conf::pk_3_malformed_manifest_fails_before_any_code`, `conf::pk_3_schema_failure_keeps_its_specific_code`, `conf::pk_3_only_a_codeless_schema_failure_is_manifest_malformed`, `conf::pk_3_subdirectory_manifest_not_read_without_a_path`, `conf::pk_3_missing_error_names_the_path_option` |
| PK-4 | **The schema artifact.** The JSON Schema **`plugin-manifest.schema.json`** (Appendix B; JSON Schema 2020-12 restricted to the keywords that MN-1, PD-2 and PD-3b use) **validates the manifest**: its top-level keys are the closed set of MN-1, and **a key outside it is `manifest_unknown_key` exactly as MN-1 defines**; every existing specific admission code of the frozen contract is preserved. The Hub validates with this artifact and with no second hand-written schema; the artifact is versioned with `botster_plugin_api`. | `conf::pk_4_manifest_validated_by_the_schema_artifact`, `conf::pk_4_unknown_top_level_key_is_manifest_unknown_key`, `conf::pk_4_existing_specific_admission_codes_are_preserved`, `conf::pk_4_no_second_hand_written_schema`, `conf::pk_4_schema_versioned_with_the_plugin_api` |
| PK-5 | **Sources and catalog entries gain `path`.** A source is `{kind: \"git\", url, ref?, path?}` and a catalog entry's `source` is `{git url, ref?, path?}` (PM-1, PM-2); a `local` source names the package root directly and has no `path`. **One repository may hold several plugins:** each is its own package, installed and locked separately, with its own `path`. The **lock record** (PM-3) gains **`source_path`**, and **the content hash covers the files under the package root only** (PM-3). | `conf::pk_5_git_source_and_catalog_entry_carry_an_optional_path`, `conf::pk_5_local_source_has_no_path`, `conf::pk_5_lock_records_source_path`, `conf::pk_5_content_hash_covers_only_the_package_root` |
| PK-6 | **Agent definitions and accessories (PM-11) use the same rule with their own file names.** Each is a package root with **exactly one** of `botster-plugin.json` (a plugin), **`botster-agent.json`** (an agent definition) or **`botster-accessory.json`** (an accessory); the package kind is the one whose file exists. **More than one of the three at one root** fails `invalid_request{detail.code: manifest_ambiguous}`. The JSON Schemas **`agent-definition.schema.json`** and **`accessory.schema.json`** (Appendix B) validate the two data files; PK-1 to PK-5 apply to them unchanged (name, root, `path`, size, single file, schema, lock). | `conf::pk_6_three_manifest_file_names_one_kind_per_root`, `conf::pk_6_two_manifests_at_one_root_is_ambiguous`, `conf::pk_6_agent_and_accessory_validated_by_their_schemas`, `conf::pk_6_same_path_size_lock_rules_apply` |
| PK-7 | **Catalog entries for multi-plugin repositories.** Two catalog entries may name the **same** `git url` and `ref` with different `path`s; each resolves, installs, locks and updates **independently**: **each package's lock records the commit that its own install resolved**, so two installs made at different times may lock **different** commits of the same repository, and neither is updated by the other. **The same commit is promised only for packages that one operation resolves together** (an explicit shared resolution: the **bulk `upgrade_packages`** resolves the whole set as one resolution, PD-6; there is **no multi-package install action** in the client contract, so installs are always separate resolutions). `status` and `outdated` (PM-10) are per package. | `conf::pk_7_two_entries_one_repo_different_paths_are_independent_packages`, `conf::pk_7_installs_at_different_times_may_lock_different_commits`, `conf::pk_7_bulk_upgrade_packages_shares_one_resolution`, `conf::pk_7_installs_are_always_separate_resolutions`, `conf::pk_7_status_and_outdated_are_per_package` |
| PK-8 | **Discovery in a target (CP-8).** In a target's plugin directory (`target_plugin_dir`), **every immediate subdirectory that holds a package manifest file is a package root**; a subdirectory with none is ignored (not an error), and one with more than one is `manifest_ambiguous`. | `conf::pk_8_each_subdirectory_with_a_manifest_is_a_package_root`, `conf::pk_8_subdirectory_without_a_manifest_is_ignored`, `conf::pk_8_subdirectory_with_two_manifests_is_ambiguous` |
| PK-9 | **Validation order.** The manifest file checks of PK-1 to PK-4 and PK-6 are **the first step of static admission** (PD-9 (A), before item (1)): the file is found, read within its bound and parsed before any other check runs, and **no plugin code, script or fixture has run**. | `conf::pk_9_manifest_file_checks_are_the_first_static_step`, `conf::pk_9_no_code_runs_before_the_manifest_is_found_and_parsed` |

**Parameters:** none added. The manifest file is bounded by the existing `package_bytes_max` (PM-4) and a `path` by the existing request bound `max_frame_bytes`.

## 2. Edits to existing J4e clauses

| J4e clause | Edit |
|---|---|
| MN-1 | Adds: "The manifest is the file `botster-plugin.json` at the package root (PK-1 to PK-4)." The key set is unchanged. |
| PM-1 | The `git` source is `{kind: "git", url, ref?, path?}` (PK-5); the `local` source names the package root. |
| PM-2 | The catalog entry `source` is `{git url, ref?, path?}` and `kind` also names the package kind of PK-6. |
| PM-3 | The lock record gains `source_path`; the content hash covers the files under the package root only (PK-2, PK-5). |
| PM-5 | Install step "stage" begins with the manifest file checks (PK-9). |
| PM-11 | Agent definitions and accessories are identified by `botster-agent.json` and `botster-accessory.json` (PK-6). |
| CP-8 | Discovery finds package roots by the rule of PK-8. |
| Appendix B | Adds the schema artifacts `agent-definition.schema.json` and `accessory.schema.json`; `plugin-manifest.schema.json` validates `botster-plugin.json` (PK-4). |
| Lua binding | No Lua call changes; LB-17 cites the manifest file name by reference to PK-1. |
