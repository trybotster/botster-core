## A3-1. The worker reports the notices in dropped output on the route (adds to DP-3, OU-1 and OU-3; matches the codec's TS-4c and A.4 `0x0F output_dropped`, revision 36)

DP-3 adopts the codec verbatim, so the worker implements the codec's `output_dropped` frame. The Core duties, in the codec's terms:

1. **Only when negotiated.** The worker sends `output_dropped` **only on a route that negotiated the route feature `output_dropped`** (OU-1 `route_features`, announced in `attached.features`). **Without the feature there is no frame and no guarantee:** the notices are lost with the discarded output. A worker advertises the feature in its own route features (A3-3); an N−1 worker without it never has the feature negotiated.
2. **When it applies.** When the worker discards the unstarted output frames of a route (a stall resync, OU-3b, or a queue overflow, the codec's `resync{overflow}`) and sends a `resync`, it considers the **notifications in the output that this route never received because of the discard**. A notification is a **bell, an OSC 9 notification or an OSC 777 notification**, as the pinned emulator classifies them (the same classification as the `Bell` and `Notification` events, A2-4). **OSC 52 is never counted** (a clipboard write is not a notification, EV-3).
3. **The notification policy decides which ones count.** Each session has a **notification policy**, which the host supplies and the worker applies **at the time of the discard** (a later change affects only later discards):
   - `NotificationPolicy` = `All` (the default) | `None` | `Matching{patterns: [string]}`.
   - **`All`:** every notification passes, a bell included. **`None`:** none passes, so no frame is sent. **`Matching`:** a notification passes when **any pattern is a substring of its text** (a literal, case-sensitive byte match on the UTF-8 text; there is no regular expression). **The policy is evaluated on the full text of the notification as parsed, before any shortening for the frame (item 4).** The **text** of an OSC 9 notification is its message; the text of an OSC 777 notification is its title and its body **joined by one newline** (`\n`). **A bell has no text and never matches.**
   - **An empty pattern `""` is valid.** It is a substring that every notification text contains, so it matches every OSC 9 and OSC 777 notification; a bell still never matches. **An empty pattern list matches nothing.** Core refuses no policy for its size or content: the policy is host-supplied policy, the host is trusted, and Core adds no bound of its own to it.
4. **What it sends.** If **at least one passing notification** was dropped, the worker sends **one** `output_dropped{notifications: count, last}` frame to that route. **`count` counts only the passing notifications. `last` is required and is the last passing one** (`source` is `bell`, `osc9` or `osc777`, with `title?`, `body?` and `truncated?`). It sends **no** frame when none passes.
   **The frame bound.** The encoded frame (the type byte plus the JSON, **including every JSON escape expansion**) must be at most the route's negotiated `route_limits.max_frame_bytes`. `count` and `source` are always exact. If the frame would be larger, the worker **shortens `body` first, then `title`, at UTF-8 character boundaries, measuring the escaped JSON size**, until the frame fits, and **sets `last.truncated: true`** (codec revision 36); the matched text of `last` is not re-evaluated after the shortening. A frame that needed no shortening has no `truncated` field. The full text stays in the host's `Notification` event (A2-4). **An empty `title` or `body` is omitted from the frame, never sent as `""`.** **The minimum frame is the worst case:** the type byte plus `{"notifications":N,"last":{"source":"osc777","truncated":true}}`, where `N` has as many decimal digits as the route's `route_queue_bytes` (the largest count a route can hold). **A route whose `max_frame_bytes` cannot carry that minimum frame does not get the feature:** the worker leaves `output_dropped` out of that route's `attached.features` (item 1), so no frame is ever too large.
5. **Order and exactly once.** The frame goes **before** the `resync` of that discard, and it reports each dropped notification **exactly once**: a notification in a frame that **started** is delivered (a started frame is always completed, the codec's TS-4c) and is not counted; a notification is never counted in two discards.
6. **A retained exception frame.** `output_dropped` is an exception frame: ordered, retained, **never discarded by a resync or by the stall that causes it**. It waits in the existing route queue under the existing `route_queue_bytes` bound, as `input_refused` and `input_done` do (OU-8). **No new bound, counter or ledger is added**; the frame is a constant size (a count and one bounded notice). A route with an `output_dropped` frame that it cannot send is a stalled route like any other (OU-2).
7. **How the worker finds them is implementation-defined.** The contract states the guarantee, not the method (non-normative: one way is to scan the discarded bytes with the parser that classifies notices).
8. **No host event, and no change to the host's events.** Core posts no new event for this. The `Bell` and `Notification` events of A2-4 are posted at parse time as before, unchanged, whatever the policy says and whatever a route did or did not receive. The host does not deduplicate against `output_dropped`: that frame is a route frame for the client, not a host event.

9. **The count bound: a queued frame is charged at its inflated size.** The width of `count` is derived from `route_queue_bytes` (codec revision 36). That bound is valid only if the queue's charge covers the output that the frames **represent**, not only the bytes that they occupy. A compressed frame (`output_deflate`, DP-3) can inflate to far more bytes than it occupies, and each notification needs at least one inflated byte (a bell is one byte), so compressed repeated bells could exceed the encoded size. **Rule (replaces "Frames queued per route" in 9B for `route_queue_bytes`):** a route's queue is charged **for each output frame the larger of its encoded size and its inflated payload size** (a plain `output` frame is its own size; an `output_deflate` frame is charged its inflated payload size, which the DP-3 bound already limits to `max_frame_bytes` − 1). Every other queued frame is charged its encoded size. So the dropped notifications of one discard never exceed `route_queue_bytes`, and `count` always fits the digits that the minimum frame reserves. This adds **no new limit**: it is the existing `route_queue_bytes`, measured on the inflated size. A route that negotiated `output_deflate` therefore reaches its stall and overflow points earlier than the encoded bytes alone would, which is the safe side.

**How the host supplies the policy.**
- `SpawnRequest` gains `notification_policy?: NotificationPolicy` (default `All`).
- **`begin(SetNotificationPolicy{session, policy})`** changes it. It completes `Ok(())` once the policy is stored: **in `Created` there is no worker, so Core stores it in the session's registry row** (the request that `Start` launches the worker with, LC-3), and the completion follows the durable write (async `RegistryFailed`); **in every other admitted state** the worker stores it (async `WorkerLinkFailed`). `Start` hands the row's policy to the new worker. Sync errors: `UnknownSession`, `WrongState`, `Unsupported` (the session's worker lacks the `notification_policy` feature, AD-4). Async: `WorkerLinkFailed`. Admitted in `Created`, `Starting`, `Running`, `Stopping`, `Exited`. The worker keeps the policy, so it survives a host restart (AD-3); a host that adopts a session reads no policy back and sets it again if it wants to change it.

**Frame list.** Where v1.17 DP-3 lists the base frames as `0x01 attached` to `0x0E output_deflate`, the list now ends at **`0x0F output_dropped`**. OU-8's text that admits only the listed frame types admits `0x0F` as a retained exception frame, only on a route that negotiated the feature.

## A3-2. Focus and stall are unchanged (confirms DP-12, the `FocusChanged` row of 6.2 and OU-2)

- **A stalled route still counts as focused as before:** `FocusChanged` and `terminal_state.focused` use the v1.17 definition (the latest `focus` input of any route), whatever the route's state. A stall and a resume post no `FocusChanged` and change no focus value.
- **DP-12 is unchanged:** a stall is not a route end, so the program gets **no focus-out** when a route stalls and no focus-in when it resumes. The synthetic focus-out is written only when a route whose latest `focus` input was `true` **closes** and no remaining route's latest `focus` input is `true`.
- **OU-2 is unchanged:** `RouteStalled{route}` and `RouteResumed{route}` carry the `RouteId` and are class M events. The resume point is the binding's progress point (OU-3a), as v1.17 says.

## A3-3. Features and the operation table (adds to A2-1 and A2-6)

- **Features (A2-6 table).** Two names are added: `output_dropped` (a **route feature**, per worker: OU-1 `route_features` and `attached.features`) and `notification_policy` (**per worker**: the session's worker accepts `SetNotificationPolicy`; an N−1 worker may lack both).
- **Operation table (A2-1).** One row is added: `SetNotificationPolicy` | `session`, `policy` | `()` | `UnknownSession`, `WrongState`, `Unsupported` | `RegistryFailed` (`Created`), `WorkerLinkFailed` (other states) | `Created`, `Starting`, `Running`, `Stopping`, `Exited`. `SpawnRequest` gains `notification_policy?`.
