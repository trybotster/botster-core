## K2. Grammar gaps (U-4, U-5, U-6, U-7, U-10)

| # | Clause | Test |
|---|---|---|
| UI-RZ-4b | **Compare function for `order`.** Absent sorts first. Then by JSON type in this order: null, bool, number, string, other. `false` < `true`. Numbers compare as **IEEE-754 doubles in every implementation**: each converts the JSON number to a double first (Rust converts `i64`, `u64` and `f64` to `f64`), `-0` equals `0`. Two integers above 2^53 that convert to the same double compare **equal** and fall back to the row-key tie-break, in Rust and in JavaScript alike; the vector includes `9007199254740993` and `9007199254740992`. Strings compare bytewise in UTF-8 exactly as written (not UTF-16 code units; JavaScript uses a UTF-8 byte compare).  Objects and arrays ("other") compare equal to each other. Ties fall back to the row key (bytewise). **`order: desc` reverses the whole value order, absent included (absent sorts last); the row-key tie-break stays ascending.** Rust and Web `realize` MUST produce the same order (UI-BD-5). | `conf::ui_rz_4b_compare_function_vectors` (includes numbers above 2^53, desc with absent, tie-break) |
| UI-FD-2 | **`Field.map` key.** For a non-string value the key is the **RFC 8785 (JCS) text** of the value: `true`, `false`, `null`; a number uses RFC 8785 number serialization, so `1.0` and `1` are both `1`, `1e21` has one spelling and `-0` is `0`. A string value matches a key equal to its own text. **A string `"true"` and the boolean `true` therefore match the same key and show the same display; this is intended.** **Key domain.** Only a string, a boolean, `null` or a **finite number** is a lookup key. An **object or an array is never a key**: it matches nothing and shows as raw text. **Raw display text.** Wherever UI-FD-2 shows a "raw value" (an unmapped value, an object, an array), a **string shows as itself** and **any other value shows as its RFC 8785 (JCS) text**, whose member order and number spelling are canonical, so every implementation draws the same characters (UI-BD-5). **Member order is UTF-16 code unit order, as RFC 8785 requires, and not UTF-8 byte order** (the string compare of UI-RZ-4b is a different rule and stays UTF-8): an implementation must not "fix" the member order to UTF-8. **Admission refuses a document that contains a number outside the double range** (such as `1e999`: JavaScript parses it to Infinity, Rust rejects it), `invalid_request{detail.code: number_out_of_range}`. A row value whose double conversion is not finite is treated as **absent** for UI-RZ-4b and for this lookup, so no implementation allocates an unbounded value. **A key matches a string value by its own text, and a number value by its RFC 8785 text** (so the key `"1.0"` matches only the string `"1.0"`, and a string field such as a version may use it). **Admission refuses a non-canonical key only when the map is over a field that the kind's schema declares numeric or boolean** (`number`, `integer`, `boolean`): a key that parses as a JSON number but is not in RFC 8785 form (`1.0`, `1e0`) on a numeric field, or `true`, `false` in another case on a boolean field, is `invalid_request{detail.code: non_canonical_map_key}` with the canonical text in the message, because such a key could never match. On a string or untyped field nothing is refused. A value with no key in `map` shows **the raw value as text in the neutral tone** (also for `status_badge`, U-10). | `conf::ui_fd_2_map_key_is_json_text_of_value`, `conf::ui_fd_2_number_key_is_rfc8785_text` (vectors 1.0, 1e21, -0), `conf::ui_fd_2_object_and_array_are_never_keys`, `conf::ui_fd_2_raw_display_text_is_rfc8785` (the vector file includes an object whose member names include a supplementary-plane character and a character above U+E000, whose UTF-16 and UTF-8 orders differ), `conf::ui_fd_2_nonfinite_number_is_absent` (vector 1e999999999), `conf::ui_fd_2_document_number_out_of_range_refused` (vector 1e999), `conf::ui_fd_2_non_canonical_map_key_refused_on_numeric_field` (vectors 1.0, 1e0 on a number field; TRUE on a boolean field), `conf::ui_fd_2_string_field_accepts_key_1_0`, `conf::ui_fd_2_string_true_equals_bool_true`, `conf::ui_fd_2_unmapped_value_shows_raw_text_neutral` |
| UI-PT-5 | **Part property types.** `form.submit` and `form.cancel`: `{ label?: string }` (literal; defaults are client copy). `actions.overflow`: `auto` or `never`, as for `toolbar`. `list.item`: `{ fields: [Field], actions?: [ActionRef] }`. `detail.source`: `{ kind, id: Operand }` (the id is a literal or any operand in scope, UI-BD-3) or `{ sel }`. `alternatives`: a boolean on a structural parent (UI-PT-3), default `false`. Admission refuses any other property type (`bad_property_type`). | `conf::ui_pt_5_property_types`, `conf::ui_pt_5_bad_type_refused` |
| UI-AC-8 | **`disabled_reason`.** The `Action` grammar gains `disabled_reason?: string` (literal copy, UI-CP-3). UI-RC-5 uses it; without it the client shows "Nothing selected". **When an action is disabled for two reasons, the pending text of UI-AC-2b wins** over the predicate or `disabled_reason` text. | `conf::ui_ac_8_disabled_reason_field`, `conf::ui_ac_8_pending_text_wins_over_disabled_reason` |

## K5. What this amendment does not change

The part set, the predicate grammar, node ids, forms, selection, the embed sandbox and channel rules, and every frozen clause not named above are unchanged. A client that supports only 1.0 to 1.2 shows a local diagnostic for a view that sets `requires: ["ui_1_3"]` (UI-CF-1). The Hub sends the same projection to every client (EN-9). **Ship together:** UI-RZ-4b gives mixed-type orders (and `desc`) a defined result, which a 1.0 to 1.2 client orders differently, so the Web and TUI clients ship ui 1.3 together; until both do, a plugin that depends on mixed-type ordering sets `requires: ["ui_1_3"]`.
