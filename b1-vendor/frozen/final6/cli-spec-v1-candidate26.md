## 1. Principles

| # | Principle |
|---|---|
| CLI-P1 | **A client, not the Hub.** The CLI speaks to the Hub only over the binding `local-stream` (HC 9.1), as a caller authenticated by socket permissions and peer uid (TB-L3). It reads and writes **no Hub file** (manifest, pid file, lock, credentials, data directory). It starts the Hub only by running the Hub's own executable (CLI-ST-2). |
| CLI-P2 | **One Hub per machine (user ruling UD-1).** One data root and one socket per user account. The CLI has no multi-Hub discovery and no `--hub` selection. A dev build and a release build share them: a developer **swaps the binary** of the one Hub (CLI-ST6, CLI-DV3). **Exemption, harness only:** the test harness runs ephemeral, isolated instances with their own temporary roots; they are not installed Hubs and no product CLI flag or command reaches them (CLI-RT3). |
| CLI-P3 | **Zero regression.** A command, flag, stdout format or exit code marked KEEP in section 10 stays as the legacy CLI behaved. Every deviation is listed in section 11 with its reason. |
| CLI-P4 | **stdout is data, stderr is diagnostics.** A command whose output an agent or script captures writes only that output to stdout. |
| CLI-P5 | **No cloud in the CLI** (ruling U-4). Sign-in, device flow, keyring, registration and the hub directory belong to the cloud plugin. The CLI stores no credential and creates no identity. |
| CLI-P6 | **No secret in a log or an error.** A pairing URL, an MCP token, a route token or a capability URL is never written to a log, a diagnostic or an error text. |
| CLI-P7 | **Additive versioning.** A new command, flag or context key is a MINOR change. A removed command, a changed stdout format, a changed exit code or a renamed key is a MAJOR change. `botster --version` prints the CLI version. |
| CLI-P8 | **Testable against FakeHub** (HC section 12). Only the launch and attach smoke tests need a real Hub. |

## 4. Roots and discovery (CLI-RT)

| # | Clause | Test |
|---|---|---|
| CLI-RT1 | **App name.** `botster` in every build, release or development. Every path below derives from it, so the two builds share **one** config root, data root and socket. Nothing in a build changes the app name. (CL-89; D-19.) | `conf::cli_rt1_app_name`, `conf::cli_rt1_dev_shares_paths` |
| CLI-RT2 | **Roots the CLI knows.** The *config root* is `BOTSTER_CONFIG_DIR`, else the platform configuration directory plus the app name (macOS `~/Library/Application Support/<app>`). | CLI-RT3 | **Hub socket discovery.** The CLI connects to exactly one socket. In order: (1) the path in `BOTSTER_HUB_SOCKET`; (2) `$BOTSTER_CONFIG_DIR/hub.sock` if `BOTSTER_CONFIG_DIR` is set; (3) `<runtime dir>/<app>/hub.sock`, where `<runtime dir>` is `$XDG_RUNTIME_DIR` if it is set, else `/tmp/botster-<uid>`. A path over 103 bytes is refused with a message that names the operating-system limit (the legacy CLI kept paths short for the 104-byte socket address limit, CL-94). **One rule for Hub, CLI and UI (HC TB-L1, unconditional):** steps (1) and (2) are honored by all three in every environment, so they always choose the same socket. They are environment variables, not product options: **no CLI flag or command selects another Hub or root**, and the product never sets them except for the UI child of CLI-AT2 (same Hub). The ephemeral instances of the test harness (CLI-P2) use them; UD-1 forbids a second *installed* Hub, and a developer who exports them by hand is outside the product contract. The Hub creates the directory with mode 0700 and the socket with mode 0600 (TB-L3). **Dependency DEP-1:** the Hub contract must state this rule; today HC names only a `socket_path` inside a route transport. | `conf::cli_rt3_discovery_order`, `conf::cli_rt3_long_path_refused` |
| CLI-RT4 | **Liveness probe.** "A Hub answers" means: the CLI connects to the socket, sends `hello`, and receives `welcome` within 500 ms (the legacy probe bound, CL-36). The CLI never reads a pid file or a manifest to decide this. | `conf::cli_rt4_probe_by_handshake` |
| CLI-RT5 | **No side effects.** No command creates a device identity, a credential, a keyring entry or a directory other than the log directory. (Legacy `start` and `status` created a device identity, CL-17 and CL-37; deviation D-1.) | `conf::cli_rt5_creates_nothing` |

## 6. `context`: the session program's launch context (CLI-CX, CG-3)

**Why this is critical.** Every local agent definition launches its program with `"$(botster context prompt)"` and `codex` reads `worktree_path`, `branch_name` and `session_dir`. The legacy CLI read a session manifest that the legacy Hub wrote. HC MC-1c gives a session only `BOTSTER_SESSION_ID`, `BOTSTER_MCP_URL`, `BOTSTER_MCP_TOKEN`, optional port variables, `BOTSTER_CONTEXT_FILE`, `TERM`/`TERMINFO` and a `PATH` that starts with the directory of the Hub's own `botster` binary. ## 9b. Plugin management (CLI-PL)

**User ruling:** full plugin management, "like lazyvim or vimplug": a URL or a local directory, catalogs, a lockfile, update, pin and rollback. 0016 specifies the feature and its wire; this section specifies the commands as a client of it. The Hub's kind is `package`; the CLI says `plugin`, the user's word. **Wire (DEP-9, bound by client contract parity21, `3f2855a0…c7f6`, name change in parity23, `cb1d061e…437d`, to HP A4r67 PM-1 to PM-14):** install = `create(package, { source })` with `source` one of `{ kind: local, path }`, `{ kind: git, url, ref? }`, `{ kind: catalog, catalog_id, entry_id }`; remove = `delete(package, { purge? })`; enable and disable = `invoke`; status = `get` or `watch` of the row's `status` (`installed`, `outdated`, `errored`, `live`, `pinned`, `staged`); update preview = `invoke(package, preview_upgrade)` (a read) and update = `invoke(package, upgrade)`; pin and unpin = `invoke(package, pin, { ref })`; rollback = `invoke(package, rollback)`; new grants = `invoke(package, approve_grants, { grants })`; all packages = `invoke(hub, preview_package_upgrades | upgrade_packages | rollback_packages)`; catalogs = `create`, `delete` or `invoke refresh` on the `catalog` kind. **A `local` source is live: it has no lock, so `pin` and `rollback` apply to `git` and `catalog` sources (PM-9); on a local one the Hub's refusal is printed.**
