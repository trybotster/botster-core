## 1. Scope and principles

**P1. The Hub owns policy.** Identity, grants, limits, restart policy, what a caller is, what a session is, and every refusal belong to the Hub. A plugin cannot widen any of them.
**P2. Trust boundary (settled).** A plugin's *code* is untrusted; its *host* is trusted to confine it. v1 admits **trusted conformant hosts only**: shipped hosts, or hosts the operator explicitly trusts (TR-1 to TR-3). The Lua host confines Lua code (section 17) and enforces a per-VM memory cap (LM-6); **the Hub checks the manifest grants on every call.** Core's OS-level service protections are optional and best effort, and hard OS isolation is post-v1; **nothing in this contract relies on Core to sandbox a plugin.** An untrusted native executable as a plugin host is later and not planned now.
**P3. One protocol, many hosts.** Every plugin-to-Hub interaction is an asynchronous, serializable frame. The Lua host, a future JavaScript or Rust host, and the conformance fakes speak the same frames.
**P4. One path per operation.** No sync and async twins. A host may present a synchronous API to its language (Lua coroutines do); the wire is always request and completion.
**P5. No polling.** Every wait ends on a frame, an event or a deadline (LM-2).
**P6. Limits are parameters** (`PluginLimits`, section 15), chosen by the host and reported to the plugin at handshake.
**P7. Errors are a closed set of kinds** (section 14). The kind is the contract; the message is for humans.
**P8. Versioning is additive and feature-detected** (section 18).
**Out of scope for 1.0:** memory accounting (process limits are Core service configuration; no plugin-facing accounting surface is frozen); federation (local Hub only); plugin-supplied UI code other than the sandboxed `embed` view (VW-10, AS-1 to AS-4) (entities plus declarative views otherwise); filesystem **writes** (HTTP, WebSocket and secrets are in v1, section 9.8; filesystem reads under an approved root are in v1, section 9.10).

## 2. Model and framing

- **Endpoints.** The *Hub side* is the Hub's plugin supervisor (one per plugin). The *host side* is the plugin process's host runtime (for Lua: the VM wrapper). The plugin's code runs inside the host side.
- **Frames.** Every frame has a lane byte, a `type` byte and a payload. **The payload is one UTF-8 JSON object** (WF-1…WF-6). Frame types 0x00–0x7F are **state-changing**: a receiver that does not understand one answers `Fault{unsupported_frame, type}` and the sender's operation completes with an error (nothing is stranded). Types 0x80–0xFF are **advisory**: an unknown one is ignored and counted (VR-2).
- **Connection epoch.** `Hello` carries `epoch` and an opaque `instance` id. **Every later frame carries the epoch.** `instance` is an opaque identifier used only for fencing and logs; scheduling counters are not on the protocol. A frame whose epoch is not the connection's current epoch is dropped and counted (CR-5). The epoch changes on every (re)connect.
- **Wire versus language mapping.** The wire carries `payload`, `caller` and `origin` as explicit fields. How a host hands them to plugin code is its choice (the Lua host calls `handler(payload, request)` with `request.caller` and `request.origin` owned by the Hub; IV-1).

| Direction | Frame | Meaning |
|---|---|---|
| Hub→plugin | `Hello` | Handshake: protocol version range, features, limits, instance, epoch, `resumed`, hub id (HS-1). |
| plugin→Hub | `Ready` | Proposed registration: handlers, tools, prompts, events, entity providers, timers to re-arm, host facts (HS-2). |
| Hub→plugin | `Activated` | The Hub published the registration atomically; application traffic may begin (HS-2). |
| Hub→plugin | `Invoke{request_id, handler, kind, payload, caller, origin, deadline_ms}` | Run one handler (IV-1). |
| Hub→plugin | `Cancel{request_id, reason}` | Cancel one invocation (IV-5). |
| plugin→Hub | `Result{request_id, result}` | The handler finished (IV-2). The Hub adds `effect` to a failure it reports to the caller (ER-5). |
| plugin→Hub | `HostCall{call_id, context, call, args, max_result_bytes}` | Ask the Hub to do one operation (CA-1). |
| Hub→plugin | `HostResult{call_id, result, effect}` | The Hub's answer; `effect` tells whether a mutating call had an effect (CA-5). |
| Hub→plugin | `Shutdown{deadline, reason}` | Orderly stop (LD-4) or refused registration (HS-2). |
| plugin→Hub | `Fault{code, detail}` | The host cannot continue (CR-2). |

There is **no `Emit` and no `Log` frame**: emitting an event and writing a log record are host calls (`events.emit`, `log.write`), so each has a context, a typed result and an `effect`. A host call of the *bulk class* (`log.write`) travels on lane 3 in both directions; every other call uses lane 2.

- **Lanes.** Four lanes, each bounded by `PluginLimits`: `control` (0: `Hello`, `Ready`, `Activated`, `Shutdown`, `Fault`, `Cancel`), `invoke` (1: `Invoke`, `Result`), `call` (2: `HostCall`, `HostResult`), `bulk` (3: bulk-class host calls such as `log.write`, and their results). Lane 0 is never starved by another lane.
- **Identity of a request and a call.** `request_id` is chosen by the Hub and is unique within the connection epoch. `call_id` is an opaque value chosen by the host and is **unique within the connection epoch** (channel-unique, not request-local), so a `HostResult` needs no `request_id`. `HostCall.context` is exactly one of `{ request: request_id }`, `bootstrap`, or `autonomous`. There is no reserved "zero" request id.
- **Who holds authority.** The Hub keeps, for every live `request_id`, the **stored caller** it wrote into the `Invoke` (`operator`, `session` or `system`). A `HostCall` with `context.request = R` acts with plugin authority (CP-3) and, for calls that need the requester's identity, with the **stored caller of R**. A `HostCall` with `context = bootstrap` or `autonomous` has no caller and cannot use caller-bound calls.

## 5. Load, unload, reload

**Generation rule (one rule).** A **generation** is one load of a plugin (on the wire: an opaque `instance`). A request belongs to the generation that was serving when the Hub admitted it, and it **finishes there**. A new request goes only to the generation that is serving when the request is routed. Reload creates generation n+1; re-adoption after a Hub restart keeps the generation and changes the epoch (CR-5).

### 9.6 What the Hub does not own

**The Hub owns no inbox, envelope, delivery or retention primitive.** A messaging plugin owns its inbox storage in its own collections, at-least-once delivery (a lease and an ack) over that storage, retention (survives a restart of the same session id until acknowledged, refuses posts to an ended session, deletes on session deletion, using the lifecycle evidence of SS-5), its access policy over the verified caller, its tools and its UI. The Hub gives it only the primitives: the verified caller (VC-1), durable plugin storage (ST-9), session safe write (SW-1 to SW-9) and session observe (SO-1 to SO-4).

## 14. Results and errors

**Two layers.** The **protocol result** (`Result`, `HostResult`) tells whether the *operation ran*. A **handler's value** is the plugin's own schema-defined JSON (for example `{ok, question}` from a tool). A handler returns a protocol success that carries **any declared JSON value**; a domain refusal (the ticket is closed) is part of that value, not a protocol failure. A protocol failure means the runtime could not do what was asked (`failed{handler_error}`, `timed_out`, `cancelled`, a crash). **For MCP:** a protocol failure is a JSON-RPC error when the call itself was refused (unknown tool, `invalid_request` from schema validation, `capability_denied`), and `isError: true` content when the handler ran and failed; a handler's declared domain refusal is ordinary content, not `isError`. (MT-5.)

`Result = { ok: true, value } | { ok: false, error: { kind, message, retryable, effect, detail? } }`. **`effect` is on every failure the caller sees**: `none` (nothing happened), `committed`, or `unknown`.

**The kind is the contract.** Kinds are a closed set and additive for *descriptive* information only (below).

| kind | meaning |
|---|---|
| `invalid_request` | argument shape or value refused |
| `capability_denied` | the package lacks the grant, or the object is not the plugin's |
| `not_found` | the named object does not exist |
| `conflict` | revision conflict or already exists |
| `quota_exceeded` | a plugin-owned quota is full (retained storage, documents, watches) |
| `response_too_large` | one result or item is larger than `max_result_bytes` or `max_frame_bytes`; nothing is truncated; not retryable as written |
| `backpressured` | a bounded queue or reservation is full now |
| `timed_out` | the deadline expired |
| `cancelled` | the plugin or the Hub cancelled the operation |
| `unavailable` | the target runtime is stopped, not ready or not configured |
| `failed` | the operation ran and failed; `detail` explains |

Specific codes travel in `detail.code` (for example `not_ended`, `remote_hub_unsupported`, `revision_conflict`, `plugin_crashed`, `wrong_context`). A host that does not know a `detail.code` still acts on `kind`.

| # | Clause | Test |
|---|---|---|
| ER-1 | Every refusal uses exactly one kind from the table. A refusal never raises in the plugin's language. **A host that receives a kind it does not know treats it as `failed`, honoring `retryable` and `effect`**; a new kind appears behind a feature name (section 18). | `conf::er_1_closed_kinds` |
| ER-2 | **`retryable` means a retry may succeed; it does not mean that repeating is safe** (the client meaning), and it is not a function of `kind` alone. **Safety to repeat comes only from `effect: none`, the same idempotency key, or an `idempotent: true` call.** | `conf::er_2_retryable_needs_no_effect`, `conf::er_2_retryable_is_not_safe_to_repeat` |
| ER-5 | **Effect at the caller seam.** A refusal **before handler dispatch** (validation, capability, queue full, stale descriptor, schema) is `effect: none`. A cancellation, timeout, crash or handler failure **after dispatch** is `effect: unknown` unless the Hub can prove no effect, and is `retryable: false` unless a resolving idempotency key exists. **Earlier host calls of the handler that committed stay committed**; `cancelled` at a deadline (LD-3, LD-4, IV-3) is never reported as zero-effect. A `HostResult.effect` (committed or none) describes **that call only** and never establishes the whole handler's atomicity. | `conf::er_5_refusal_before_dispatch_is_none`, `conf::er_5_cancel_after_dispatch_is_unknown`, `conf::er_5_earlier_calls_stay_committed`, `conf::er_5_host_result_effect_is_per_call` |

## 17. Hosts: trust, what stays language-local, the published sandbox

**Trust boundary (user decision via the orchestrator).** v1 admits **trusted conformant plugin hosts only**: the Hub launches shipped hosts, or hosts the operator explicitly trusts. **Plugin code inside a host is untrusted and is confined by that host**; the Hub enforces manifest permissions on every call. **Untrusted native host executables are out of v1** (they need OS-level confinement, a later contract). The protocol stays language-neutral so later trusted hosts (another language) are possible.

| # | Clause | Test |
|---|---|---|
| TR-1 | **Host allowlist.** The Hub starts only a host executable that is (a) shipped with the Hub, or (b) on the operator's trusted-host list by path and digest. ## 18. Versioning

- **Protocol number** `plugin_protocol_version` (integer). The Hub supports `[min, current]` (HS-3). A change an existing plugin cannot ignore raises the number; everything else is additive.
- **Additive rules.** New fields, new `call` names, new `kind`s for *descriptive* values, new `detail.code`s, new event names and new limits are additive. A new call or frame type appears behind a feature name first (HS-4). Unknown **descriptive** fields are ignored and counted.
- **Fail closed on authority and state.** An unknown capability, caller kind, handler kind, frame type in the state-changing range, or mutating operation **fails closed** (refused, never mapped to an "other" that acts). Unknown enum values are "other" only for purely descriptive fields.
- **Features.** `Hello.features` lists what the Hub offers; `Ready.features.required` must all be offered or the load fails; `Ready.features.optional` are selected by **intersection**. A feature name never changes meaning under the same name; a changed meaning is a new name.
- **Manifest.** The manifest declares **`botster_plugin_api: 1`** (an integer: the plugin API major version the plugin targets, the field of the approved platform manifest); the Hub refuses a load whose value it does not support (`unsupported_plugin_api`).
- **Change process.** One pull request carries, together, the clause, the conformance test, the fake's behavior and the frame schema; a reviewer other than the author signs off.
- **Support promise.** The Hub supports **the current protocol and the previous one (current-1), and no other** (as Core AD-4 and client HS-2).

| # | Clause | Test |
|---|---|---|
| VR-1 | A plugin host built at the previous protocol version loads and runs against the current Hub. | `conf::vr_1_previous_version_loads` |
| VR-2 | An unknown **advisory** frame (0x80–0xFF) or descriptive field is ignored and counted. An unknown **state-changing** frame type is refused with `Fault{unsupported_frame}` and the operation completes with an error; it is never silently ignored. | `conf::vr_2_unknown_advisory_ignored`, `conf::vr_2_unknown_state_changing_refused` |

## 19. Independent conformance

**Goal (as in Core).** A bug is fixed on one side without the other side's tests changing.

- **The contract crate** `botster-plugin-contract`: the frame types, `Result`, `ErrorKind`, `PluginLimits`, `Features`, the call list and the clause text as rustdoc, plus the JSON schemas of the frames (generated).
- **The suite** `botster-plugin-conformance`: clauses as **frame scripts** (data: an ordered list of frames to send and the frames to expect, with a clause id), plus a small runner. Scripts are language-neutral, so a host in any language can run them.
- **Two fakes, written from the clauses, not from real code**, each under **1.5k lines** (if it needs more, the contract is too large):
  - **`FakePlugin`**: a scripted plugin process. It drives a real or fake Hub: handshake, registration, handlers that return scripted results, host calls, crashes at chosen points, slow handlers, oversize frames. Used to test the **Hub side**.
  - **`FakeHub`**: a deterministic Hub endpoint. It drives a real plugin host (Lua or another): `Hello`, `Invoke`, scripted `HostResult`s, deadline and `Cancel`, `Shutdown`, channel close. Used to test the **host side** and for **plugin authors** to test their plugin without a real Hub.
- **Seeded interleaving (the important part).** `with_seed(n)` randomizes every order the contract leaves open: order across lanes (MD-1), order of concurrent invocations (IV-6), event delivery order across emitters (EV-4), batching of frames, spurious `Cancel` races, which events are shed under pressure. The suite and the Hub's tests run under many seeds. A test that passes on one seed and fails on another depends on an order the contract does not promise.
- **Real runs** (small and named): a real Lua host loads a fixture plugin under the real Hub; a plugin crash mid-request; a Hub restart with an adopted plugin; a reload; a flood of events with a slow plugin; MCP tool call from a real session token.
- **Hub CI check.** Every host call the Hub implements maps to a clause and a test id. A plugin-facing call with no clause is an unverified dependency. The Lua host CI check: every `botster.*` function in the ABI doc maps to a `call` name here, or to section 17.
- **A behavior in a fake with no clause and no test is not allowed.**

## 20. Migration note: what leaves today's Lua runtime (informative, non-normative)

*This section is a migration note. No clause depends on it, and it never changes a clause.*

Today's runtime is a **thread host** inside the Hub process with an in-process engine. The contract replaces the in-process calls with frames and keeps the **semantics**. Carry over as logic (not as code): handler registration and validation, the capability table, the result shape and error kinds, the event router statuses, the session-family baseline protocol, plugin_db rules, plugin logs, session-type spawn policy, entity publish statuses and windows. Delete: in-process shared state between the Hub and a plugin, the closure-based registries, and the thread-host-only accounting hooks. The Lua host becomes a separate binary that speaks the frames; it is the first conformance subject.

## 21. The service transport: adopts Core section 10

**One model, stated once, in Core.** This contract **adopts section 10 (SV) of the Core contract by contract name and clause id only** (`contracts-v1-joint-manifest.md` maps the name to its file and hash) and **does not restate it**, so a change in Core cannot silently change this contract. The needs below cite Core by clause id only.

| Plugin-contract need | Core clause |
|---|---|
| Four lanes (`control`, `invoke`, `call`, `bulk`); lane meaning is the Hub's | SV-3, SV-4 (`lanes`) |
| The Hub's `Hello` is the first frame on lane 0 | SV-2 |
| A full lane never starves `control` | SV-3 (independent lanes) |
| Adoption after a Hub restart: old connection work is cancelled, process memory is kept | SV-6 (epoch: all lanes reset together) and MD-4, CR-5 |
| `orphan_grace` enforced while the host is dead; the plugin host need not observe EOF | SV-8 (guardian) |
| Crash cause and stderr tail for diagnosis | SV-5, SV-9 |
| The Hub never infers a limit cause from an exit signal (Core gives none) | SV-5 |

**Agreed with the Core pair (2026-09-30).** The plugin contract accepts the **current SV-2** (Core listens, the service connects, one authenticated connection per lane, one staged epoch across all lanes, guardian-owned orphan grace). Corrections that follow from the orchestrator's trust ruling and from the Core pair: there is **no `SandboxSpec` in Core 0.1** (a future sandbox needs its own feature contract; the Hub's v1 confinement is the trusted host plus the host allowlist, TR-1 to TR-3); optional **unsupported OS bounds are reported, never a launch refusal**; there is **no portable hard per-service memory cap**, so plugin memory is the host's per-plugin cap (`host_memory_bytes`, LM-6, LM-7); hard OS isolation is post-v1. **The Hub marks no OS bound "required" in v1**: generic Core may let a caller require one (and refuse launch when it is unavailable), but every OS bound the Hub requests is optional and reported, never a launch refusal. `service_recv` returns **the epoch with every retained frame**, and the contract promises **no preservation of received-but-unread frames across a host crash** (library memory dies with the host): after adoption the host re-handshakes (CR-5), and only frames the host had already read are the host's to keep.

**Not asked of Core:** restart policy, replay, payload parsing, handshake content, lane meaning, timers, plugin vocabulary.

## 22. Open for the user

Only choices that belong to the user remain:

**Decided by the user (2026-09-30):** (1) **One Hub runs on a machine, never more**: no multi-local-Hub support, no Hub-to-Hub socket RPC, no cross-Hub posting on one machine (VC-8). (2) **An integration with an external service is a plugin** (a separate product, not a concern of this architecture): the contract names **nothing service-specific and has no service credential placeholder**; it is built from the generic primitives `net`, `ws`, `secrets`, `events`, `mcp_servers` and `plugins.call`, and the generic primitive it lacked, hashing and signing, is language-local `crypto` (section 17). (3) **Repo-scoped packages are auto-discovered per enabled spawn target**, and the Hub-wide firing is fixed (CP-8). (4) **A public tunnel is an ordinary plugin-run command** (`process_run`, PX-4), with no special contract text. (5) **The web plugin** may set the web origin that pairing URLs use, relay WebRTC signalling as an **untrusted** relay, serve the web app statically from its own origin, and negotiate with the website over `net` and `ws` (WP-1 to WP-5); **general session forwarding and connector plugins stay out of v1**. (6) **Agents are clients**: tool permissions are scoped, the package and secret tools are not operator-only, and the default grant for an agent is broad and operator-restrictable (CP-9). (7) **Plugin-supplied HTML is allowed as the `embed` view kind**, shown in a sandboxed iframe from a separate assets origin with no access to the app's origin or credentials (VW-10, AS-1 to AS-4). (8) **Full plugin management** (user: \"like lazyvim or vimplug; point it at a URL or a local directory, it connects\"): local, git and catalog sources, a lockfile with content hashes, install, update with a preview, pin, rollback, enable, disable, remove and status, agent definitions and accessories on the same model, and no plugin code at install (section 9.14, PM-1 to PM-14). **Nothing is open for the user** beyond the final sign-off. **Declarative `mcp_servers` are in v1** (user decision 2026-09-30, feature `mcp_proxy`, section 11.1, MP-1 to MP-15). **Connection primitives are in v1** (section 9.8: `http.request`, outbound WebSocket, `secrets.get`, inbound local webhooks); raw TCP is not.

**No other user decision is open.** Answered 2026-09-30: **U8** untrusted native hosts are **later, not in v1 and not planned now**; **U9** (superseded by the 2026-09-30 reversal) the Hub owns **no** inbox: the messaging plugin owns storage, lease and ack, retention (survives a restart of the same id until acknowledged, refuses posts while the session is ended, deletes on deletion), and its access policy over the verified caller, on the Hub primitives `sessions.safe_write` (and the raw `sessions.write`), session observe, verified caller and durable storage (ST-9, section 9.6). The user also confirmed that messaging is a plugin and that plugins can provide UIs through the UI Nodes vocabulary (section 12, VW-6, VW-7).

Settled and not repeated as questions: JSON payload (technical); public plugin events (required, approved); own-spawned default plus operator-approved `:any` (settled; recording the spawning plugin is an implementation requirement); transient Hub timers (technical v1 choice); restart once then quarantine (approved, plugin-platform section 18; numbers are Hub parameters); the Hub's safe-input mechanism versus the messaging plugin's text and ring policy; side-by-side reload (our design choice, LD-3); per-VM memory cap (orchestrator ruling); trusted conformant hosts only (orchestrator ruling).

### 25.3 The plugin definition (identity, requirements, dependencies)

The **definition of a plugin** is the manifest (MN-1) read as a contract: **who it is, what it needs, and which interfaces it provides and requires.** It is validated **before any code runs**.

| # | Clause | Test |
|---|---|---|
| PD-1 | **Identity.** The manifest declares **`name`** (the plugin key: lowercase letters, digits and `-`, no `@`, no `__`), **`version`** (a semantic version `MAJOR.MINOR.PATCH`, `semver 2.0.0`; a manifest whose version does not parse fails the load `invalid_request{detail.code: manifest_bad_version}`), and optionally `description`, `license` (an SPDX identifier) and `source` (informational only: the source that the package manager **recorded at install** is the truth, PM-1). | `conf::pd_1_name_and_version_required_and_valid`, `conf::pd_1_source_field_is_informational_only`, `conf::pd_1_license_is_optional` |
