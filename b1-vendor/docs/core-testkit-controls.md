# Core test controls beyond FakeCore's

Design 6.3 defines test controls: inputs that only a test can cause. FakeCore implements the first list in `docs/fake-core-notes.md`
(`fail_next`, `lose_worker`, `break_control`, `descendants`, `pty_chunk`, `pty_blocked`, `pty_input`, `pty_output`, `withhold_feature`,
`unavailable_bound`, `control_queue`, `revisions`), and `oracle_encode` is real-only. FakeCore is frozen, so the controls below are for the
real Core testkit and for the slow tier (BUILD.md, "Phases"). A transcript that uses one lists it in `requires.controls`. A subject without it
gives `unsupported_control`, which is never a pass.

Every control is built from the injected parts of the testkit (Core A5-1, A6-1: program, storage, process, route transport, service lane,
wake and scheduler edges, and the real libghostty oracle, steward rule R-7). A control is never a branch in production code (BUILD.md,
Testing rule 8), and never a contract obligation.

## The real-tier forms of the program controls

On a real-process harness, the program edge is the production probe (`botster-conformance-probe`) on a real PTY that the production
worker started. The harness reaches it through the probe's control socket (`botster_probe_script::control`; steward approval of
2026-10-10). The harness names the socket in `CoreHarness::probe_env`, and the driver adds it to the `env` of each `Create`, so no
transcript names it (Core A5-4). After its terminal setup (R-48) and before its first step, the probe connects and names its pid and
its parent's (the session's worker, which spawns the payload as its direct child), so the harness finds a session's probe by the worker
of Core's registry row; a probe that cannot
connect exits with `CONNECT_FAILED_EXIT` (69), a setup failure, never a pass. A probe whose stdin is a terminal and whose R-48 setup
fails (`tcgetattr` or `tcsetattr` returns an error) exits with `TERMINAL_SETUP_FAILED_EXIT` (71) before its first step, also a setup
failure: it never runs on a canonical terminal in silence (steward ruling R-74). A control returns when the probe acknowledges the request
(the request is then in effect); it never waits for a write to complete.

- `program_ready`: the probe has connected. It connects only after its R-48 terminal setup is complete (or at once when stdin is not a
  terminal), so input after it is never echoed (steward ruling R-60).
- `pty_output`: the probe writes the bytes to its terminal.
- `pty_input`: every byte that the probe read from its terminal, in order. One reader thread owns stdin, and `print_after_input`
  matches the reader's log.
- `pty_blocked`: the probe makes no `read` call until `on: false`, so the kernel buffer fills and the worker's write would block
  (R-47 item 7). `on: false` also removes a `pty_accept` limit. The real tier ignores `kernel_bytes`: the kernel buffers.
- `pty_queued`: `FIONREAD` on the probe's stdin, the bytes that wait in the kernel buffer. The probe answers with the count and changes
  nothing (R-74). Linux counts only the line discipline's buffer (4095 bytes on 6.12), not the bytes in the tty's flip buffers, and
  fills that buffer asynchronously: the count is a lower bound that grows, so only `>= 1` is a fence.
- `pty_accept`: the probe reads at most this many more bytes, then stops as for `pty_blocked`.
- `pty_chunk`: each read of the probe takes at most this many bytes.

The kernel buffer lies between the worker's write and the probe's read, so a byte count at the worker's write (IN-2) can exceed what
the probe read. A transcript asserts no kernel count; the steward rules each such step (R-47 (A)).

## Held writes (steward ruling R-74)

A write that a transcript cancels or cuts while the worker is writing it (IN-2 `Partial`, IN-6, IN-7, AM-2) must be held by the PTY. On a
real PTY a small write is taken whole by the kernel buffer, so the held state is built like this:

1. `pty_blocked` with `on: true` and `kernel_bytes: 1`. On the testkit, `kernel_bytes: n` lets n more bytes in, unread by the program,
   and then takes none; `pty_queued` reports them, and `on: false` delivers them in order. The real tier ignores it (the kernel buffers).
   Only the held-write transcripts pass it; every other `pty_blocked` is unchanged.
2. The write under test carries **F = 40960 bytes** (`HELD_WRITE_FILL_BYTES` in `botster-core-conformance`). F is twice the largest
   measured capacity of a non-canonical PTY with no reader, and it is at most the default `max_paste_bytes` (1 MiB):

   | OS | Capacity (non-canonical, write until `EAGAIN`) |
   |---|---|
   | macOS 27, arm64 | 1022 bytes, with 4096-byte and 1-byte writes |
   | Linux 6.12, x86_64 | 11776 bytes with 4096-byte writes, 20480 bytes with 1-byte writes |

   A canonical terminal is no held state: macOS takes every write and drops the bytes. R-48 makes every real session non-canonical, and
   the probe fails its setup loudly otherwise (above).
3. The fence: `await_control` on `pty_queued` with `{"bytes": {"$between": [1, 40960]}}`. Then the worker has written and its write
   blocks. The value itself is a kernel count and is never asserted.
4. Before reading `pty_input`: `pty_blocked` with `on: false`, then `await_pty` for the written count, so the log is complete. The
   count is the variable that the write's `Completed` binds. The fence lint (R-56) takes it as a capture's fence when a `pump_until`
   or `pump_collect` bound it in an earlier step, from a `WriteInput` of the same session, at `pty_bytes_written`, or at
   `payload_bytes_written` for a raw `bytes` payload only (R-74, the lint case).

A write that must never start (A2-2: cancelled before its first byte, `Cancelled` with 0 and 0) cannot be built by a cancel that races a
small write, because real Core starts the write before the cancel arrives. It waits behind a held filler write of F bytes instead
(AM-2): blocked, the filler, the `pty_queued` fence, then the write and its cancel; then the filler ends, and the log holds none of the
write's bytes.

FakeCore is frozen (BUILD.md: no new fidelity), so it has neither `kernel_bytes` nor `pty_queued`. Each held-write transcript is
`"fake": "structural"`.

## The comparator and the real-tier form of `oracle_resume`

Steward ruling R-62. The code is in the Core testkit, and both tiers use the same comparator. This repository holds only the
specification, because it stays free of libghostty (BUILD.md).

**The comparator.** It compares two oracle terminals (pinned libghostty, R-7) field by field through libghostty's own state. It
never runs the subject's snapshot encoder (GHOSTSNP). The fields and their readings:

| Field | Reading |
|---|---|
| cells and their attributes, hyperlinks | libghostty's cell and hyperlink reads, for every cell of the screen |
| cursor (position, pending wrap, visibility, style) | libghostty's terminal reads |
| modes | libghostty's mode read, for every mode |
| palette and dynamic colors | libghostty's color reads |
| title and cwd | libghostty's terminal reads |
| tab stops, margins (the scrolling region) and charsets | libghostty's formatter (`GhosttyFormatterTerminalExtra.tabstops`, `scrolling_region`, `screen.charsets`). The formatter is libghostty's code and not the snapshot encoder: at the pinned Ghostty SHA, no file of the snapshot encoder (`src/terminal/snapshot/`, `src/terminal/c/snapshot.zig`) imports the formatter. If a later pin makes the encoder call the formatter for one of these fields, that field needs another reading (R-62 follow-up F3a) |
| the saved cursor | DECRC (`1b38`) on each compared oracle terminal, last or on a clone, then compare the cursor position, the cursor style, the pen (rendition), the charsets and origin mode, which DECRC restores. It touches only the harness's oracle terminals, never the subject (F3b) |

**The completeness test (required).** For each field in the list, two oracle terminals that differ only in that field compare
unequal. It finds a comparator, or a formatter reading, that does not see a field.

**The testkit form (R-67).** The same two comparisons as the real tier, with two differences. O_raw applies the output that the
testkit logged at the program edge (`ModelLog`), so the testkit needs no `unknown_output_history` refusal. Comparison 2 decodes
the worker's `model_snapshot`, read after the model has applied every logged byte, instead of a second capture. The comparator
never touches the live model.

**The real-tier form.** The model is in the worker process, so the real tier reads it through an independent anchor:
- **O_raw** is a fresh oracle terminal of the session's size and color profile that applies every output byte that the program
  wrote, from the session's start, in order. These bytes are the transcript's own `pty_output` bytes of the session; the harness
  never asks the subject for them.
- **O_resume** is a fresh oracle terminal that loads the capture's pages, then applies every `pty_output` byte of the session that
  the transcript sends after the capture step.
- `equal` is true only if both comparisons hold:
  1. O_resume equals O_raw (the resume invariant). A capture that dropped state makes O_resume differ.
  2. A second capture, taken when the control runs, decoded into an oracle terminal, equals O_raw (the session's model). An encoder
     that dropped state fails here too, because O_raw holds that state.
- **The second capture runs only at a quiet point (R-69).** The control begins its own `CaptureSnapshot`, pumps with no clock
  step, and polls. If a poll returns any event other than the capture's own `Completed`, the result is `unsupported_control` with
  the name `events_pending` (`ControlError::UnsupportedFor`), never a pass, and the transcript ends there. The control never holds
  or re-injects a drained event. On success it reads every page, then releases the capture, so the open captures and
  `next_deadline` are as before. The testkit form needs no such check: `model_snapshot` never polls.

**Conditions.**
1. The output history must be known. A session whose program writes output that the transcript does not state (a scripted print,
   an echo, a query reply that the program renders) gives `unsupported_control` with the name `unknown_output_history`
   (`ControlError::UnsupportedFor`), never a pass. A `hold` program writes only its `pty_output` bytes.
2. Fences. Each capture follows an `await_title` on a sentinel title in the session's `pty_output` bytes (R-57): the capture step,
   and the `oracle_resume` step that takes the second capture. Where a title at the end would change the cut (a cut inside an SGR
   sequence), the sentinel goes before the unfinished tail, in the same `pty_output`. A wrong cut gives only a false failure; the
   evidence is N real runs, N ≥ 5 on macOS.
3. Size and profile. O_raw and O_resume use the size and the `ColorProfile` that the transcript set. A transcript that resizes or
   changes the profile during the history needs its own ruling.
4. Bytes. The `pty_output` bytes of a session that a later `oracle_resume` reads contain no `0a` and no other byte that `OPOST`
   changes (R-60, R-62 Q3). The oracle applies the bytes unchanged on both tiers and never models the line discipline.
5. The quiet point (R-69). Before `oracle_resume`, a waiting step (R-61(a)) consumes every event that the session's last output
   causes: a `pump_collect` of those events, after the `await_title` of condition 2. The set comes from the clauses, not from a
   run: `Activity{source: Output}` for any output (6.2), `TitleChanged` for an OSC 0 or 2 title, and `ModesChanged` for a mode
   change (EV-7). No later step expects or forbids an event that this fence consumes.

## The exact duration form

An attach option that is a `Duration` (`query_deadline`, `stall_deadline`; Core OU-1, A7-1) is written as a whole number of milliseconds in a transcript, as before, or as `{"ns": <u64>}`, which the runner turns into exactly `Duration::from_nanos(n)` and passes to the same real call (`attach`). A value below one millisecond, such as the positive `query_deadline` that A7-1 refuses, needs the second form: the contract type is a `Duration`, and whole milliseconds would lose the sub-millisecond part.

The same two forms are read by one function (`duration_of` in the Core driver) at every Duration-valued argument of a step: `advance_clock.ms`, `real_wait.ms`, `wait_wake.timeout_ms` and the `ms` of the call `set_silence_threshold` (`null` or no `ms` still turns the threshold off). `tests/driver_steps.rs` checks that `{"ns": 500000}` reaches the attach call as exactly 500 microseconds, that each step argument takes the exact form, and that the millisecond form keeps its meaning.
