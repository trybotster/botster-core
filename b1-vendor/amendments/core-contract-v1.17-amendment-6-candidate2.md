# Core contract v1.17, Amendment 6 — candidate 2 (service lanes in the testkit, the first worker protocol, uploads at Remove)

The base files are the Core contract of `frozen/current` (manifest final12): v1.17, Amendments 2 to 5, and erratum 1. They are unchanged except where A6-4 names a replacement. Other contracts are cited by contract name and clause id only.

**Supersedes candidate 1** (`8332c662…8289`, commit `37f083b`), which the Amendment reviewer rejected (`verdicts/amendments.md`, verdict `8cbf2a7`):
1. **A6-3 covers worker loss during Remove.** Losing the worker or its report at any point gives `NotDeleted{reason: outcome_unknown}`, with no paths claimed. The teardown continues. `Deleted` needs a complete report from a worker authenticated under AD-6.
2. **A6-2 enumerates the deferred set**, with a start condition for each id:
   - the unreachable branch of `conf::dp_12_unreachable_or_n_minus_1_worker_leaves_focused_unknown` stays active;
   - an "absent on the previous worker" case for a capability that the pinned previous worker already has is not applicable, and it is recorded as such.
3. **A6-3 states ownership and observable behavior only.** It no longer prescribes how or whether Core records upload names.

A6-1 is unchanged from candidate 1.

Author: the contract steward. Reviewer: the Amendment reviewer (Sol). Date: 2026-10-01. A6-1 was found by the Foundation lead while it built the replacement map. A6-2 and A6-3 were found by the Stage 1 Core lead (questions Q2 and Q5).

## A6-3. Uploaded files at Remove (clarifies LC-7 step 3 and DP-5b)

| # | Clause | Test |
|---|---|---|
| A6-3 | **Core owns the deletion of the files that the session's routes uploaded, and it reports the outcome honestly.**<br>- **When:** at LC-7 step 3. How Core finds the files is Core's choice.<br>- **The teardown always continues.** A failed delete, a worker that cannot be reached, a worker lost during the cleanup, and a lost report do not stop it. Steps 4 and 5 still run, and the session id becomes free. A stray worker is ended as LC-7 says.<br>- **The report:** `Completed{Remove}` carries `RemoveReport{ uploads }`. `RemoveReport` is non-exhaustive. Remove's only asynchronous error stays `RegistryFailed` (A2-1). `uploads` is exactly one of:<br>&nbsp;&nbsp;- `Deleted`: the cleanup **completed**, and every uploaded file is gone, or there were none. It is reported only from a complete cleanup result whose source Core trusts: the worker authenticated under AD-6, or Core itself;<br>&nbsp;&nbsp;- `NotDeleted{ reason: delete_failed, paths }`: the cleanup completed, and `paths` are **exactly** the files that could not be deleted (for example `EACCES` or `EIO`). Every other uploaded file is gone;<br>&nbsp;&nbsp;- `NotDeleted{ reason: outcome_unknown }`: the cleanup did not complete with a trusted result. The worker was unreachable, the worker was lost during the cleanup, the result was lost, or the result came from a link that failed AD-6. Any number of uploaded files may remain, and **no path is claimed**.<br>- **The host owns its directories** (OU-1 `file_directory`). A host that gives each session its own directory can delete that directory itself, whatever the report says. The Hub→client contract's data-root layout (RT-2, `sessions/<session_id>/uploads/`) does this.<br>- **DP-5b's** "deleted at `Remove` (LC-7) at the latest" means "deleted at `Remove`, or reported as not deleted in `RemoveReport`". | `conf::a6_3_uploads_deleted_at_remove_report_deleted`, `conf::a6_3_delete_failure_does_not_stop_teardown_and_lists_exact_paths`, `conf::a6_3_unreachable_worker_reports_outcome_unknown`, `conf::a6_3_worker_lost_during_cleanup_reports_outcome_unknown`, `conf::a6_3_lost_result_reports_outcome_unknown`, `conf::a6_3_unauthenticated_result_is_not_trusted` |
