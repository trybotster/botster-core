# Hub→client contract, Amendment 8 (candidate 1): the Hub terminates WebRTC; routes are channels on the client's one Hub peer connection

The base is the Hub→client contract of `frozen/current` (manifest final35), with Amendments 1 to 6, which are unchanged except where A8-7 names a replacement. HC Amendment 7 (in review) touches no clause named here. Other contracts are cited by contract name and clause id only. **The route codec extract changes with this amendment:** revision 37 applies A8-7 to the codec's copies of the same clauses (the codec header: "The client contract owns this text").

Author: the contract steward. Reviewer: the Amendment reviewer (Sol). Date: 2026-10-09. Authority:
- **a user decision, relayed by the orchestrator on 2026-10-09:** WebRTC moves out of Core and into the Hub. The Hub terminates WebRTC and bridges each route's data channel to a Core `Stream`. The trade-offs are accepted: a remote client reconnects when the Hub restarts, the Hub sees the plaintext route bytes, and there is one extra local hop. Core's side is Core Amendment 17;
- **the orchestrator's decisions of 2026-10-09, under the user's delegation:**
  - D1: route channels ride the client's one Hub peer connection. This settles the open item of section 13, "The `webrtc` binding's layout".
  - D2: route chunking is the Hub's, at `welcome.limits.max_chunk_bytes`, and `max_chunk_bytes` leaves `route_limits`.
  - Every route channel is chunked so that a large frame on one route cannot delay another route (A8-3).

**Why.** Today the session worker terminates each route's own peer connection: TR-2, TB-W2, BP-1, BP-4, BP-7 and TB-W4, with Core DP-2, DP-3 and OU-3. Core Amendment 17 removes WebRTC from Core, so the route peer moves to the Hub. The Hub already terminates the client's control peer connection, and that connection is already mutually authenticated (PR-4 to PR-9). PR-8 already reads "no `hello`, no data and no route channel on that peer connection" before authentication. A route channel on that same connection inherits its authentication, so the per-route offer, answer, signature and fingerprint of TB-W2 and BP-4 are no longer needed.

## A8-7. Text replaced

The same replacements apply to the route codec extract's copies of these clauses (revision 37).

1. **TS-1:** in the answer, `route_limits` loses `max_chunk_bytes`. "**`max_chunk_bytes` is not a frame bound:** it bounds one transport chunk, for a binding that chunks." reads "**Chunking is not a route limit:** a binding that chunks uses `welcome.limits.max_chunk_bytes` for every channel (TR-3, A8-3)." So `attached.limits`, which "restates the attach's `route_limits`" (A.4 `0x01`), has no `max_chunk_bytes`.
2. **TR-2** reads: "**WebRTC.** Signalling stays outside the envelope. The client's **Hub peer connection** carries one reliable, ordered `control` DataChannel for the envelope, watches and event streams, and **one reliable, ordered DataChannel per route** (A8-1, A8-2). Every channel ends at the Hub, which bridges each route channel to the session's worker (A8-1)."
3. **TB-W2** reads: "**Route connect.** `transport = { binding: "webrtc" }`. The client opens, on the same Hub peer connection, a reliable, ordered DataChannel labelled `route:<route_id>` within `limits.route_connect_seconds`, as A8-2 states."
4. **BP-4** reads: "**Route authentication.** A route channel is authenticated by its peer connection (PR-4 to PR-9). The Hub accepts it only for a route that the same caller reserved on the same connection (A8-2). No route secret, signature or fingerprint exists."
5. **BP-1** reads with A8-5: its sentences hold for `local-stream`. On `webrtc` the route ends at the Hub's bridge. **BP-6**, "`webrtc` over loopback", is the topology client ↔ Hub peer connection ↔ Hub bridge ↔ local stream ↔ worker ↔ PTY. **BP-7** reads with A8-5. **BP-5** and the **Layering** note: "the worker carries those payloads verbatim" adds "and on `webrtc` the Hub's bridge relays the frames unchanged (A8-3)".
6. **TR-3:** "Each chunk is at most `welcome.limits.max_chunk_bytes` on the control channel, and at most **`route_limits.max_chunk_bytes`** on a route (each chosen at or below the SCTP maximum message size)" reads "Each chunk is at most `welcome.limits.max_chunk_bytes` on every channel, chosen at or below the SCTP maximum message size (A8-3)". The rest of TR-3 stands.
7. **TB-W4** reads: "**Progress, backpressure and close** on a route channel: A8-4."
8. **Section 9.3,** "from the web plugin for the Hub and its workers (HP WP)" reads "from the web plugin for the Hub (HP WP)".
9. **Section 13,** the open item "The `webrtc` binding's layout: one control channel, plus one peer connection and channel per route (TR-2, TB-W2)" is resolved by A8-1 and A8-2.
10. **A.9,** the row `session` `attach_offer` is removed (A8-6). **Amendment 2, A.9b,** the row `session` `attach_offer` is removed.
11. **Amendment 2, the Hub configuration table,** the row `[limits]` gains `route_send_buffer_bytes` (A8-4), with the same "restart" rule as the row's other entries. It is not reported in `welcome.limits`.
12. **The route codec extract's** sentence "the stream and WebRTC progress points restate Core OU-3a (TB-L4, TB-W4)" reads "the stream progress point restates Core OU-3a (TB-L4), and the WebRTC one is the Hub bridge's (TB-W4, HC A8-4)".

Every other clause is unchanged.
