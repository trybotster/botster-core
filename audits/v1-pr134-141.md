**Reverts:** no finding needs a revert. Every CONTRACT finding can be fixed forward:
- No release depends on the current behavior.
- The production gaps are either small (A4, A5) or in paths that the next packages own (A1, A2: P5 adoption).
- The test-rule violations (A7, A8) are confined to the slow tier.

**Overall judgment.** The architecture is sound, and several pieces are elegant:
- the sans-IO `HostEngine` with ONE `HostDriver` for real Core and the testkit;
- the sans-IO `Worker` machine;
- the thin libghostty binding with correct `SAFETY` invariants;
- the `GroupGuard` anchor design;
- the per-module control registry.

No Rust code parses terminal output, tracks modes or writes expected terminal bytes. P35 holds across all eight PRs.

The quality problems are systematic, not random. They come from how the code was grown, by review finding and by surviving mutant, with the same model family writing and reviewing:
1. **Edge paths that no end-to-end test drives:**
   - adoption, then Remove (A9);
   - Create over a durable row (A2);
   - the 64-byte admission bound (A3).
2. **Tests that certify the implementation instead of the clause:**
   - a stub pinned as AD-1 (A1);
   - asserts on private engine state (A17, A18);
   - tautologies (A20, A40);
   - truth tables of one-line helpers (A33, A59);
   - pinned orders that the contract leaves open (A21);
   - a `review.rs` organised by finding number (A22).
3. **Mutation exclusions that are wider than their reasons, or that rest on tautological tests** (A14, A15, A32). The lead's "NO broad regex" rule was not enforced.
4. **Real-process tests that still break the testing rules:**
   - polling (A7);
   - an unowned worker group (A8);
   - unbounded blocking waits (A11, A24);
   - a race with the production reaper (A10).

These fit the recorded 45-minute Mac hangs.

### Per PR

- **#134 (P2 libghostty binding): good.**
  - What is good: a genuinely thin wrapper. All terminal semantics come from libghostty calls. Every `unsafe` has a correct SAFETY comment. The P38 and P32 fixes are proven. The offline build is careful.

    - the storage `Failed`/`Uncertain` split and the EV-5b held frame are careful work;
    - the E3-1 and R-20 `Switched` scheduler tests are excellent.
  - What is weak:
    - five contract deviations (A1 to A5) and one hang (A9);

  - The largest PR and the most findings.

  - What is good: the `Worker` machine and its tests (public inputs, real frames), the `LinkWritten` close accounting, the safe `waitid(WNOWAIT)` exit watch, and the Mac `EVFILT_READ` fix.
  - What is weak:

    - the slow fixtures break the process-group rule and have unbounded waits (A8, A11).
- **#137 (TI-1 wiring): correct and small.** `term` and the terminfo source now come from libghostty. Its test checks the wiring only, which is acceptable.

### A1  [CONTRACT]  `AdoptAll` silently skips damaged, other-version and colliding rows (no `SessionState`, no `Lost`), and a test pins the skip

- Sub-auditor ids: P-3, T-1. Crate: `botster-core-host`.
- Lead auditor note: Merged: P-3 (production) and T-1 (the test that pins it). P5 owns the AD-1 recovery of live workers, but the shipped behavior and its test contradict AD-1 now, and P-2 (A2) builds on the skip. No revert: fix forward, and stop certifying the stub.

**From P-3 (CONTRACT): `AdoptAll` silently skips damaged, other-version and colliding rows (no `SessionState`, no `Lost`), and a test pins the skip**
- Location: `crates/botster-core-host/src/run.rs:627-628` (`if let Ok(row) = serde_json::from_slice::<Row>(&bytes)` / `if row.version == ROW_VERSION && !self.sessions.contains_key(&row.id)`, with no else); `crates/botster-core-sys/src/storage.rs:166` (`list_rows` drops a file whose header does not decode); test `crates/botster-core-host/src/tests/flow_edges.rs:215-264` ("a damaged row is left", "another version is left")
- PR: #135
- What: A row that fails to parse, has another `version`, or whose id is already in memory produces no event and no session. Its file stays on disk, and its id is free, which P-2 then lets a `Create` overwrite. The storage layer also drops a row file whose key header is damaged before the engine sees it.
- Why: AD-1: "`begin(AdoptAll)` reads the registry and recovers **every** row … Every other row that cannot be recovered becomes `Lost(reason)`. Each row posts one `SessionState`." AD-2 lists `RegistryCorrupt`. LC-11 has `conf::lc_11_adoptall_posts_a_state_for_every_row`. `conf::a10_2_corrupted_row_is_lost_registry_corrupt` is in `core-pending.txt`, so the gap is known. However, the shipped behavior and its test assert the opposite of the clause, not "pending".
- Fix: Post `Lost(RegistryCorrupt)` for an unparseable or unknown-version row, using the id from the row key (`session/<id>`). Have `list_rows` return undecodable files as a typed corrupt entry instead of dropping them. Replace the "is left" assertions.
- Revert needed?: no
- Confidence: high

**From T-1 (CONTRACT): The AdoptAll unit test certifies a P5 stub as AD-1 behavior; the cited clause says the opposite**
- Location: `crates/botster-core-host/src/tests/flow_edges.rs:215-267`, with asserts at 248-259; production stub at `crates/botster-core-host/src/run.rs:620-633`
- PR: #135
- What: the doc reads "Core AD-1, LC-9: … a row of a session that ran is `Lost`, a row that is damaged or of another version is left". The test asserts:
  - `get(&sid("bad")).is_err()` for a hand-written `b"{not json"` row, and the same for a `"version": 99` row;
  - `SessionState::Lost(LostReason::Other)` for a row that ran.

  Production says outright that this is a placeholder: "A row that names a worker needs the adoption handshake (AD-6), which P5 builds."
- Why:
  - AD-1 says: "recovers **every** row … Every other row that cannot be recovered becomes `Lost(reason)`."
  - A10-2 says: a corrupted row "becomes `Lost(RegistryCorrupt)` (AD-2)", and "The testkit never hand-writes a registry format."
  - BUILD.md rule 3 says: "Every expected value … is fixed by a cited clause sentence."

  The test's expected values are fixed by the stub, not by AD-1, and they contradict AD-1. `conf::a10_2_*`, `ad_1_created_rows_kept` and `ad_2_lost_reasons` are still listed in `conformance/core-pending.txt`, so the stub is a known gap. A test that pins it as clause behavior will have to be inverted when P5 lands, and until then it reads as proof.
- Fix:
  - Keep only the `Created` row assertion and the "existing session is not replaced" assertion.
  - Drop the "left" and `Lost(Other)` assertions, or mark them in a comment as P5-pending.
  - Do not hand-write row bytes.
- Revert needed?: no. The problem is in the test only, and the production stub is declared P5 scope.
- Confidence: high on the contradiction.

### A2  [CONTRACT]  `Create` checks only the in-memory table, so it overwrites a durable row (and its worker identity and token) of a session the handle has not adopted

- Sub-auditor ids: P-2. Crate: `botster-core-host`.
- Lead auditor note: Lead auditor verified `admit.rs:180` (only `self.sessions` is checked).
- Location: `crates/botster-core-host/src/admit.rs:180-185` (IdInUse checks `self.sessions` only); `crates/botster-core-host/src/flows.rs:72-82` and `:87` (the Create row write replaces `session/<id>`); pinned by `crates/botster-core-host/src/tests/flow_edges.rs:234-236` (`again.ok(create("kept"))` succeeds on a handle whose registry already holds `session/kept`)
- PR: #135
- What: A new handle starts with an empty `sessions` map. Until `AdoptAll` runs, or forever for rows `AdoptAll` skips (P-3), `begin(Create{id})` is admitted for an id with a live registry row. Its `WriteRow` then replaces that row with a new instance and no worker identity or token. The earlier worker becomes unfindable and unadoptable.
- Why: ID-1: "A `SessionId` … is **unique among registry rows**." LC-3: "A duplicate id is `IdInUse`." AD-2: a `Lost` row "keeps the worker's identity … the id stays `IdInUse` until `Remove`". AD-6 depends on the row to find the worker again.
- Fix: Make the admission table know the durable ids. For example, `Core::open` could list the row keys (the facade owns storage and may do IO) and pass them in `EngineConfig`, so `check_arguments` refuses them with `IdInUse`. Or refuse `Create` until `AdoptAll` has completed. Change the `flow_edges` test to expect `IdInUse`.
- Revert needed?: no (fix forward; no released data yet)
- Confidence: high

### A3  [CONTRACT]  The IN-9 admission bound is a fixed 64 bytes per event and ignores the unbounded `KeyInput.text`

- Sub-auditor ids: P-4, T-10. Crate: `botster-core-host`.
- Lead auditor note: Merged: P-4 (production bound) and T-10 (tests that pin 64). Lead auditor verified `admit.rs:20` and `held_bytes` at `admit.rs:410-420` (Key: `repeat * 64`, `text` ignored).

**From P-4 (CONTRACT): The IN-9 admission bound is a fixed 64 bytes per event and ignores the unbounded `KeyInput.text`**
- Location: `crates/botster-core-host/src/admit.rs:20` (`const WORST_CASE_SEQUENCE_BYTES: u64 = 64`), `:364` (Key check), `:417` (`held_bytes` for Key)
- PR: #135
- What: `KeyInput.text: Option<String>` has no length bound in `botster-core-contract` (`input.rs:23`) and no check in `check_payload`. Under legacy encoding a printable key with `text` writes "the UTF-8 of `text`". Under kitty flags 8 and 16 it adds the associated text as code points. So a `Key` with a 100 KB `text` and `repeat = 1000` is admitted against a 64 000-byte "worst case". `held_bytes` feeds the lane bound (IN-5) and `Unknown{max_payload_bytes}` (IN-2), so both understate. The 64 itself is not derived from any clause or from the encoder, and the comment admits the worker "must never produce a longer one", which nothing enforces.
- Why: 5.1A: Core computes "the worst-case encoded size over every possible mode (… the longest key sequence of any legacy or kitty flag combination, **including every modifier parameter and associated text**) … so a tiny admission can never expand into an unbounded loop or allocation." IN-2: `Unknown{max_payload_bytes}` is an upper bound.
- Fix: Compute the bound from the event: a fixed CSI overhead, derived from the encoder tables or measured from libghostty's encoder over all 32 flag sets, plus the encoded `text` length in its worst form (legacy UTF-8 or kitty decimal code points), times `repeat`. Check `text` against `max_paste_bytes` too. Add a test that exercises a long `text`.
- Revert needed?: no
- Confidence: high

**From T-10 (MEDIUM): A hand-picked worst-case size (64 bytes per semantic payload) is pinned as if a clause fixed it**
- Location:
  - `boundaries.rs:339-364` (`held_bytes_counts_each_kind`, asserts 64 and 192 on the `pub(crate)` helper `held_bytes`)
  - `boundaries.rs:215-272` (repeat or notch 3 refused at `max_paste_bytes = 128`)
  - `queue_pressure.rs:825-836` (`held_bytes(..repeat 100..) == 6400`, appended to an unrelated test)
  - constant at `admit.rs:20`
- PR: #135
- What: no clause, amendment or ruling at the tag contains 64.
- Why:
  - Core 5.1A, "Wheel magnitude", requires "the worst-case encoded size over every possible mode … the longest key sequence of **any** legacy or kitty flag combination, including every modifier parameter and associated text".
  - That value comes from libghostty's encoders. P35 and BUILD.md say expected terminal values are never hand-written, and rule 3 requires a cited clause for every expected value.
  - Every key in these tests has `text: None`, so a long `KeyInput.text` is never checked against the bound. `held_bytes` appears to ignore `text` (`admit.rs:416-418`). That is unverified and is for the admit slice.
- Fix:
  - Derive the worst case from the libghostty encoders, or get a steward ruling.
  - Test admission behavior (`PayloadTooLarge` at the derived bound), including a key with text.
  - Delete the direct `held_bytes` asserts.
- Confidence: high on the citation gap; medium on the `text` under-count.

### A6  [CONTRACT]  OSC 5522 writes above libghostty's own 64 MiB transaction limit are silent, and libghostty (not the worker) answers them with EFBIG

- Sub-auditor ids: G-1. Crate: `botster-terminal-ghostty`.
- Lead auditor note: Lead auditor verified the Amendment 13 EV-3 text at the tag ("never silent"; A13-1b "the worker is the only source of the acknowledgement"). The fix needs a Ghostty fork patch: follow the fork policy (rebase on upstream first).
- Location: `crates/botster-terminal-ghostty/src/lib.rs:113-142` (no `GHOSTTY_TERMINAL_OPT_CLIPBOARD_WRITE_MAX_BYTES` (39) is set; `sys.rs:91-111` does not declare it), `src/events.rs:308-384` (the only place a write is surfaced), `src/events.rs:433-473` (where the library's EFBIG ack lands)
- PR: #134
- What: The binding applies `clipboard_bytes` inside `on_clipboard_write` "by size alone". But libghostty first buffers each OSC 5522 transaction up to its own `kitty_clipboard_write_max_bytes` (default 64 MiB, `terminal.h:2250-2270`). Data past that limit "fails the whole transaction with EFBIG … and nothing reaches the clipboard write callback". The pinned code is `stream_terminal.zig:1524-1529` (`error.TooLarge => kittyClipboardFinish(state, .EFBIG, …)`). So a write over 64 MiB produces no `ClipboardWrite` event and no `too_large`. Its acknowledgement (`status=EFBIG`) is written by the model on its own and goes to `Drained::pty_writes`, not `clipboard_acks`, because `shared.ack` is `None`. Up to 64 MiB per transaction is also buffered natively, against a contract memory bound of 1 MiB.
- Why: Amendment 13 replaces EV-3 with: "A write larger than `CoreLimits.clipboard_bytes` (a memory bound, not a filter) is **never silent**: it is surfaced with `contents: none`, `total_bytes` and `reason: TooLarge`." A13-1b says the worker is "the only source of the acknowledgement", that the status is `SUCCESS` or `IO_ERROR`, and that "Core never answers DENIED, UNSUPPORTED or BUSY by its own choice". An EFBIG produced by the model breaks the one-owner/one-path rule, and the write is silent. Neither `libghostty-audit.md` (Revision 9, P25) nor any test considers the library-side limit. Invalid base64 behaves the same way (`EINVAL`, no callback), but whether such a write counts as "recognized" is arguable.
- Fix: Add a fork patch so an aborted-too-large transaction still calls the write callback with `total_bytes` and no contents (or a size-only report), with the reply decided by the binding. Then set option 39 to about `clipboard_bytes + 1` so native memory follows the contract bound. Add a test with a transaction just over the native limit, using a small limit through the option.
- Revert needed?: no. The gap is at the edge (over 64 MiB) and fits in a forward fix; nothing else depends on the current behavior.
- Confidence: high on the mechanism (verified in the pinned Zig and header); medium on how far it reaches, because the worker does not consume the binding yet.

### A9  [HIGH]  `Remove` of a session restored by `AdoptAll` with a recorded worker identity never completes

- Sub-auditor ids: P-1. Crate: `botster-core-host`.
- Lead auditor note: Lead auditor verified `run.rs:645` (identity restored from the row) and `flows.rs:578-597` (re-kill and re-arm with no exit source for a non-child).
- Location: `crates/botster-core-host/src/run.rs:645` (adopted session gets `worker.identity` from the row, `gone = false`); `crates/botster-core-host/src/flows.rs:517-528` (SendRemove: kill and wait); `crates/botster-core-host/src/flows.rs:578-597` (`remove_grace_expired` re-kills and re-arms forever); `crates/botster-core-host/src/inbound.rs:584-596` (`worker.gone` is set only by `ProcessExited`)
- PR: #135
- What: After a restart, `AdoptAll` restores every non-`Created` row as `Lost(Other)` with `session.worker.identity = row.worker.map(..)` and `gone = false`. Removing such a session takes the `else if let Some(identity) = worker` arm. That arm sends `SignalGroup{Kill}`, leaves `worker_gone = false` and arms `stop_grace`. Step 4 waits for `worker_gone`. Only `Input::ProcessExited` sets it, and `Children::poll_exit` reports only children of this handle. A worker from the previous host is not a child. The kill is also skipped silently when the identity no longer matches (`process.rs:187`). Each `stop_grace`, `remove_grace_expired` re-kills and re-arms, and the step never advances. `HostEdges` has no `identity_state` call, so the engine cannot learn that the process is `Absent`.
- Why: AM-3: "Exactly one completion per admitted operation". LC-7: "`Completed{Remove}` is posted only after step 5 … (for `Lost`, a stray worker is ended if one is found)". AD-2: the id "stays `IdInUse` until `Remove`", so these ids are stuck forever. Every host restart with non-`Created` rows hits this. No test covers Remove after AdoptAll (`slow_real_core.rs` adopts only a `Created` row).
